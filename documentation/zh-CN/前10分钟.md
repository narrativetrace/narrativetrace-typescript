# 前 10 分钟

[English](../first-10-minutes.md) | [Español](../es/primeros-10-minutos.md) | [Português](../pt-BR/primeiros-10-minutos.md) | **简体中文**

一个极小的服务、一个 Vitest 测试、七个步骤。下面的每一条命令都真实运行在
这个版本的仓库上——文件路径、清晰度评分,以及 `[REDACTED]` 标记都是真实
输出,不是示意图。你机器上唯一会不一样的是耗时(`ms`)和由两个单词组成的
`trace_name`,二者都是每次运行时重新生成的。

Node 20+(CI 运行 22)、TypeScript 5.0+(用于第 7 步中的装饰器)、一个已经能运行
`vitest run` 的项目。如果你还没见过更完整的全貌,从仓库根目录执行
`pnpm run build && pnpm demo -- --example ecommerce --no-pause` 会更快
——这一页是给你想在*自己的*代码上看看效果时用的。

## 1. 添加依赖包

```bash
pnpm add @narrativetrace/core-node @narrativetrace/proxy
pnpm add -D @narrativetrace/vitest
```

`core-node` 重新导出了 `@narrativetrace/core` 中的所有内容,并注册了
Node id 生成器——单独导入 `@narrativetrace/core` 会在第一次被追踪的调用
时抛出异常。这里没有需要应用的构建工具插件;这些包就是全部的依赖配置。

## 2. 添加一个服务类

```ts
// src/order-service.ts
export class OrderService {
  placeOrder(customerId: string, productId: string, quantity: number): string {
    return `ORD-${customerId}-${productId}-${quantity}`;
  }
}
```

不需要声明接口——`traceObject()` 直接用 ES `Proxy` 包装具体对象,因此
没有什么需要去实现的接口。(NarrativeTrace 的 JDK/JVM 实现的动态代理
需要一个接口;这个版本不需要。)

## 3. 添加一个 Vitest 测试

```ts
// src/order-service.test.ts
import { traceObject } from "@narrativetrace/proxy";
import { createNarrativeTest } from "@narrativetrace/vitest";
import { OrderService } from "./order-service.js";

const test = createNarrativeTest();

test("customer places order", ({ narrativeContext }) => {
  const service = traceObject(new OrderService(), narrativeContext, {
    placeOrder: ["customerId", "productId", "quantity"],
  });

  service.placeOrder("C-1234", "SKU-KB", 2);
});
```

`createNarrativeTest()` 返回一个 Vitest 的 `test`,它会为每个测试注入
一个全新的 `narrativeContext`,并在测试结束后写出追踪产物。`traceObject`
的第三个参数——`{ placeOrder: [...] }`——提供了参数名,因为 JavaScript
在运行时不会保留参数名;如果不提供,追踪中会显示 `arg0`、`arg1`、
`arg2`。(第 7 步展示了装饰器形式 `@traced`,它对你自己拥有的类做同样的
事。)

## 4. 运行测试套件

```bash
npx vitest run
```

输出落在 `narrativetrace-output/` 下——因为没有指定 `outputDir`,这是
夹具选取的默认目录——每个场景每种格式各一个文件:

```text
narrativetrace-output/
   |
   +-- order-service/customer_places_order.md          human narrative
   +-- order-service/customer_places_order.json         same trace, JSON
   +-- diagrams/order-service/customer_places_order.mmd Mermaid sequence diagram
```

`order-service.test.ts` 变成了 `order-service` 目录(测试*文件*的名字,
经过净化处理——相当于 Java 中测试*类*目录的平台等价物);`"customer places
order"` 变成了 `customer_places_order.md`——测试名,转换为 slug。没有其他
需要配置的东西。默认只会写出 `md`/`json`/`mmd`;想要 `puml`、
`clarity-json` 或 `canonical-json`,把 `formats: [...]` 传给
`createNarrativeTest`——见[安装指南](安装指南.md#3-配置追踪输出)。

## 5. 打开叙事文件

`narrativetrace-output/order-service/customer_places_order.md`:

```markdown
---
type: trace
scenario: customer places order
entry_point: OrderService.placeOrder
duration_ms: 1.548
trace_id: 7919d16fd10a133f3f1ebf9f5670c502
trace_name: tidy mink roots
method_count: 1
error_count: 0
---

- `OrderService.placeOrder(customerId: "C-1234", productId: "SKU-KB", quantity: 2)` → `"ORD-C-1234-SKU-KB-2"` — 1.548ms
```

调用流程中的每一个值——参数值、返回值——都来自你真正发起的那次调用。没有
任何一处是手写的。

## 6. 把 `placeOrder` 改名为 `process`,看清晰度下降

命名质量是被测量出来的,而不是被断言出来的。一旦你在 `formats` 中加入
`"clarity-json"`,`createNarrativeTest` 就会额外写出
`customer_places_order.clarity-json`。改名之前,针对这个具体场景:

```json
{
  "overallScore": 0.94,
  "methodNameScore": 0.91,
  "classNameScore": 0.96,
  "parameterNameScore": 0.95,
  "structuralScore": 1,
  "cohesionScore": 0.9,
  "issues": []
}
```

把方法(声明、`paramNames` 键,以及调用点)改名为 `process`,再次运行
`npx vitest run`:

```json
{
  "overallScore": 0.79,
  "methodNameScore": 0.4,
  "classNameScore": 0.96,
  "parameterNameScore": 0.95,
  "structuralScore": 1,
  "cohesionScore": 0.9,
  "issues": [
    {
      "category": "method-name",
      "element": "OrderService.process",
      "suggestion": "Use a domain-specific verb+noun (e.g., calculateTotal, reserveInventory)",
      "severity": "MEDIUM",
      "occurrences": 1,
      "impactScore": 2
    }
  ]
}
```

同样的调用、同样的值、除了名字之外一切都没变——总体评分从 0.94 掉到了
0.79,方法名这一维度单独从 0.91 掉到了 0.40,并且出现了一条问题。套件级别
的 `clarity-report.md` / `clarity-results.json`(汇总每个场景,并带有你
设置的通过/失败阈值)还需要多一个步骤——把 `ClaritySuiteReporter` 加入你
的 Vitest `reporters`——具体见
[清晰度指南](清晰度指南.md#从-vitest-生成结果文件)。继续之前,把它改回
`placeOrder`(或者改成更具体的名字)。

## 7. 添加 `@notTraced` 并查看脱敏效果

```ts
// src/order-service.ts
import { notTraced, traced } from "@narrativetrace/proxy";

export class OrderService {
  @traced("customerId", "productId", "quantity", "paymentToken")
  @notTraced(3)
  placeOrder(customerId: string, productId: string, quantity: number, paymentToken: string): string {
    return `ORD-${customerId}-${productId}-${quantity}`;
  }
}
```

`@traced` 取代了第 3 步中的 `paramNames` 映射——有了这个装饰器,
`traceObject(new OrderService(), narrativeContext)` 就不再需要第三个
参数。`@notTraced(3)` 把参数索引 3(`paymentToken`)标记为需要脱敏。在
测试中传入一个令牌(`service.placeOrder("C-1234", "SKU-KB", 2,
"tok_live_51H8x9J")`)并再次运行。这次的追踪:

```markdown
- `OrderService.placeOrder(customerId: "C-1234", productId: "SKU-KB", quantity: 2, paymentToken: [REDACTED])` → `"ORD-C-1234-SKU-KB-2"` — 1.005ms
```

参数名依然会出现——你能看出*确实*传入了一个令牌——但它的值永远不会落到磁
盘上。脱敏还覆盖了哪些内容,包括针对那些不是逐个参数构造的对象的字段级
脱敏(`static notTraced`),见[隐私与脱敏](隐私与脱敏.md)。
