# 选择集成方式

[English](../choosing-an-integration.md) | [Español](../es/eligiendo-una-integracion.md) | [Português](../pt-BR/escolhendo-uma-integracao.md) | **简体中文**

NarrativeTrace 只有一种捕获模型——一个进入/退出事件,由 `traceObject()` 的
ES `Proxy` 构建,发布到 `NarrativeContext`——但可以通过多个不同的接入点到
达它。这一页回答"我到底需要哪个包",先给出一张速查表,再给出一张决策
图,最后列出每条路径各自的注意事项。

## 你想要... / 从这里开始...

| 你想要 | 从这里开始 |
|---|---|
| 在测试里获得追踪,接线最少 | `@narrativetrace/vitest`(`createNarrativeTest`) |
| 在纯 TypeScript/JavaScript 里精确选择要包装什么 | 直接使用 `@narrativetrace/proxy`(`traceObject`) |
| Express 应用中按请求的追踪 | `@narrativetrace/express` |
| Hono(边缘/无服务器)中按请求的追踪 | `@narrativetrace/hono` |
| 零应用代码的 Nest provider 追踪 | `@narrativetrace/nestjs`(`AutoProxyModule`) |
| Angular 服务/DI 追踪 + HTTP 关联 | `@narrativetrace/angular` |
| React 组件/服务追踪 | `@narrativetrace/react`(导航场景另加 `@narrativetrace/react-router`) |
| 使用打包工具(bundler)的浏览器页面 | `@narrativetrace/core-web` + `@narrativetrace/browser` |
| 浏览器页面,不用打包工具,经典 `<script>` | `@narrativetrace/standalone` |
| Node 上跨请求/异步的可见性 | `AsyncNarrativeContext`(`@narrativetrace/core-node`,基于 `AsyncLocalStorage`) |
| 同一追踪下的并行工作 | `ForkJoinGroup` / `FireAndForgetGroup`(`@narrativetrace/core`) |
| 生产日志流中的追踪 | `@narrativetrace/winston` 或 `@narrativetrace/pino` |
| OpenTelemetry span | `@narrativetrace/opentelemetry` |

这与[根 README](../../自述文件.md#选择你的集成方式)中的矩阵相同;它也放在
这里,作为下文决策图与详细说明的锚点。

## 这个决策

```text
调用发生在哪里?

Vitest 测试
   |
   +--> @narrativetrace/vitest(createNarrativeTest)

纯 TypeScript/JavaScript——你自己构造对象
   |
   +--> 直接使用 @narrativetrace/proxy(traceObject)

Express / Hono 请求处理函数
   |
   +--> 对应的中间件包,每个请求一个 AsyncNarrativeContext

NestJS provider 关系图
   |
   +--> @narrativetrace/nestjs——不改动任何调用点,DI 包装每一个 provider

Angular / React 组件树
   |
   +--> @narrativetrace/angular 或 @narrativetrace/react

没有框架的浏览器页面
   |
   +-- 有打包工具       --> @narrativetrace/core-web + @narrativetrace/browser
   +-- 没有打包工具     --> @narrativetrace/standalone(经典 <script>)
```

每一条分支最终都走向同一个 `traceObject()`/`Proxy` 机制——中间件或 DI 模块
只是一个包装器,决定*何时*调用它、把它交给*哪个* `NarrativeContext`,而绝
不是第二条捕获路径。这是刻意的设计,而不是疏漏:`require`/ESM 加载器钩子
被否决,是因为 JS 在运行时不保留参数名(注解已经承担了这项职责),而且加
载器插桩在打包工具、浏览器和边缘运行时里会被完全绕过——在这些场景下,
`Proxy` 才是标准做法。

## 每条路径共有的一点

上面所有这些包都通过同一个 `NarrativeContext` / `DualPathPipeline`
(`@narrativetrace/core`)发布;它们都没有各自定义"被捕获的调用"这个概
念。选择一种集成方式,回答的是*调用如何被包装、由哪个上下文接收它*这个问
题,而绝不是一旦被记录后会记录成什么样。

## 各路径的注意事项

- **`traceObject`(proxy)**——一次包装一个对象;没有接口要求(不同于
  JVM 动态代理),因为 `Proxy` 直接包装具体对象本身。通过属性查找可
  达的每一个方法——无论是自有的还是从原型链继承来的——都会被包装;直接
  在未包装的实例上发起的调用会完全绕过追踪,而且 `#private` 字段完全无法
  被 `Proxy` 拦截——这是 JavaScript 语言本身的限制,不是缺陷。
- **Express / Hono**——每个请求一次 `AsyncNarrativeContext.run()`,这正
  是防止并发请求相互串入对方追踪的关键;跳过这一步、让多个请求共享同一
  个上下文,是一个正确性缺陷,而不是什么便利做法。
- **NestJS**——`AutoProxyModule.forRoot(...)` 会包装交给它的每一个
  provider;目前该模块内部没有按方法退出的选项——要么缩小交给它的范围,
  要么在不想捕获值的方法上加 `@notTraced`。
- **跨线程工作**——Node 没有线程可跨,但异步工作仍然需要显式传播:
  `AsyncNarrativeContext` 会自动跟随 `await`,但一个被发起而*没有*被等待
  的任务(定时器、即发即弃的 promise、Worker)不会自动继承当前活跃的
  span。对你自己拥有的任务,使用 `ForkJoinGroup`/`FireAndForgetGroup`;
  或者用 `context.snapshot()` + `snapshot.wrap(...)` 手动把游离的工作接回
  父追踪。
- **浏览器**——`SyncNarrativeContext` 完全没有隐式传播(浏览器里没有
  `AsyncLocalStorage`);在同一个上下文上重叠的、未被等待的调用会相互破
  坏。对每个并发任务使用显式的 fork/fire-and-forget 分组,做法与上面异
  步工作的注意事项相同。

## 平台上限

这个平台上没有零代码的、"包装一个你无法修改的应用"的路径——没有等价于
Java Agent 的东西,也没有计划做。`TC39` 装饰器和 `traceObject()` 都需要
一个调用点,或者一个你能加注解的类;`require`/ESM 加载器钩子被刻意否决了
(在不同 Node 版本间很脆弱,而且在打包工具、浏览器和边缘运行时里会被完全
绕过——在这些场景下,`Proxy` 才是标准做法)。
