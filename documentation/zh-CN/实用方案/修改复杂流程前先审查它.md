# 修改复杂流程前先审查它

[English](../../recipes/review-a-complex-flow-before-changing-it.md) | [Español](../../es/recetas/revisa-un-flujo-complejo-antes-de-cambiarlo.md) | [Português](../../pt-BR/receitas/revise-um-fluxo-complexo-antes-de-altera-lo.md) | **简体中文**

## 问题

> 在你改结账流程之前,告诉我它实际上做了什么。

阅读源码回答的是它*能*做什么。一次运行回答的是它在这些输入下*做了*什么——按什么顺序、用了
哪些值,以及流程在哪里离开了你即将编辑的代码。本页刻意从不展示实现:这正是读运行而不是读
源码的意义所在。

## 最小配置

追踪产物除了[安装](../安装指南.md)和 `@narrativetrace/vitest` 之外什么都不需要。日志行需要
日志桥接及其接线,与[给这个服务加日志](给这个服务加日志.md)中完全一样。捕获级别是一项设置,
本页除了默认的 `detail` 之外,还会用到 `summary`:

```ts
const test = createNarrativeTest({ level: "summary" }); // or NARRATIVETRACE_LEVEL=summary
// "off" | "errors" | "summary" | "narrative" | "detail"
```

参见[配置指南第 1 节](../配置指南.md#1-追踪级别narrativetraceconfig)。

## 场景

对这个流程的一次有代表性的运行——借用一个现成的测试成本最低,这就是那个测试:

```ts
// fixtures/checkout-review-fixture.ts
import { createNarrativeTest } from "@narrativetrace/vitest";
import { expect } from "vitest";
import { tracedCheckout } from "../support/wiring.js";

const test = createNarrativeTest();

/**
 * One successful checkout, the flow documentation/recipes/review-a-complex-flow-before-changing-it.md
 * is read before changing anything.
 *
 * A fixture because the page needs the same run under two capture levels:
 * `__tests__/review-flow-recipe.test.ts` runs it in a nested Vitest process once at the default
 * level and once at `summary`. It passes either way — nothing here fails by design.
 */
test("a customer buys two keyboards", ({ narrativeContext }) => {
  const { checkout, stock, repository } = tracedCheckout(narrativeContext);

  const orderId = checkout.placeOrder("C-1234", "SKU-KB", 2, "4242424242424242");

  expect(orderId).toBe("ORD-C-1234-SKU-KB-2");
  expect(stock.availableUnits("SKU-KB")).toBe(3);
  expect(repository.saved()).toHaveLength(1);
});
```

## 如何阅读

**流程,来自 `detail` 产物。** `#1` 是测试发起的那次调用,也是唯一的根:缩进在它下面的一切
都发生在它之内,顺序就是打印的顺序。`#1.1` 在任何扣款之前预留两件;`#1.2` 扣款 7998——
两件各 3999,所以价格是由数量算出来的,不是传进来的;`#1.3` 保存的订单已经带着 `#1` 返回的
id。读成一句话:这个结账流程先预留、再扣款、后保存,而且订单 id 在保存之前就已生成。先扣款
再预留、或先保存再扣款的改动,改变的就是*这个*,而现在你不必相信某条注释就能知道它。

**每个级别的用途。** `detail` 携带参数值,是你处理这个流程时阅读的那一份。在 `summary` 下,
每个参数值都被省略——是在捕获时抑制,而不是在渲染时隐藏:名字还在,后面什么都没有——并且
只保留根调用和叶子调用;这个流程只有两层深,没有中间调用,所以出现的还是同样的四次调用。
更深的流程会丢掉它的中间部分。返回值在每个启用的级别都保留:返回值是叙事的载荷。`narrative`
介于两者之间,是完整的调用流程但不含值。当你需要的是形态和结果、而值是成本时——一次 CI
运行、一次长时间浸泡测试——用 `summary`;在生产环境用 `off`/`errors`,直到你需要更多。

**哪份输出给人读,哪份给智能体读。** 日志行是给值班的人看的:它们与服务写出的其他所有日志
交错在一起,带着值,并以追踪的名字——`solid wand romps`——为键,所以一次结账可以从繁忙的
文件里 grep 出来。`.nt` 是给智能体和评审者看的:**构造上就不含值**——把它和上面的日志行
比较一下,区别不是值被替换了,而是它们从未被写入。`(customerId, sku, quantity, cardNumber)`
是参数*名*;`→ value` 表示返回了一个值,但没有说是哪个。这使它可以安全地提交、在评审中做
差异比较、交给模型:它不可能泄露客户 id,而且数据变了它也不会变——只有*调用*变了它才会变。
把它固定下来就是
[审查重构:行为变了吗](审查重构行为变了吗.md)。

## 没有捕获什么

- **未包装类内部的调用。** 包装了四个对象;它们背后两个类之间的调用,或者私有方法,永远不会
  出现。看起来很浅的流程可能其实很深。
- **所选集成方式不拦截的内容。** Proxy 只看得到*经过*被包装引用发起的调用:类对自己发起的
  内部调用(`this.helper()`)对它是不可见的——`InMemoryInventory.reserve` 会去问它自己的
  `availableUnits`,而没有出现 `#1.1.1`。
  [选择集成方式](../选择集成方式.md)按路径逐一讲了取舍,而这正是其中会改变你在这里能读到什么
  的那一部分。
- **离开了进程的工作。** 对工作线程或另一个服务的调用运行在它自己的上下文里;追踪在本进程
  被包装的工作结束的地方结束,除非把追踪标识一并传过去
  ([框架集成指南](../框架集成指南.md))。
- **被拒绝列表或值形态规则拦住的值**,这里是 `cardNumber` 和 `card`,在日志和 `detail` 产物
  里都是 `[REDACTED]`,而在 `.nt` 里按构造就不存在。
- **一次运行,不是契约。** 换一个输入会走另一条路径——缺货的 sku 根本到不了 `#1.2`。

**对应的技能:** `narrativetrace-verify`——它先写下意图,运行最小的真实路径,并在任何事情被
称为完成之前,对照那份意图阅读不含值的追踪。
