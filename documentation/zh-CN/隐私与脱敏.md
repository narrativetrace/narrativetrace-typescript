# 隐私与脱敏

[English](../privacy-and-redaction.md) | [Español](../es/privacidad-y-ocultacion.md) | [Português](../pt-BR/privacidade-e-ocultacao.md) | **简体中文**

这个库运行在你的进程内部,写出的文件会被你的团队共享——测试产物、CI 输出、生产日志行。这一页是这份契约逐行展开的版本:哪些内容会被脱敏、脱敏能覆盖到哪里、覆盖不到哪里,以及 NarrativeTrace 保证什么、又完全不对什么做出承诺。已于 2026-09-02 逐行对照代码验证过,不是从文档里推断出来的。

## 脱敏,逐个界面来看

| 界面 | 能否关闭内置脱敏? |
|---|---|
| `traceObject()`(proxy)——`express`、`hono`、`angular`、`react` 都构建在其上的捕获路径 | 不能 |
| `AutoProxyModule`(`@narrativetrace/nestjs`)——它自己独立的、直接修改 prototype 的捕获路径,*不是*构建在 `traceObject()` 之上(见下文说明) | 不能 |
| Vitest 夹具(`createNarrativeTest`/`narrativeTest`) | 不能 |
| 你自己的代码直接调用 `renderValue()`/`renderStructured()` | 能——但只有显式传入 `{ redactionPolicy: RedactionPolicy.DISABLED }` 才行,而且即便如此,`@notTraced`/`static notTraced` 依然会脱敏(见下文) |
| `@notTraced` / `static notTraced` | 不适用——它本身就是执行脱敏的那一方,并且在每一个界面上都永远优先,包括一个 `RedactionPolicy.DISABLED` 的渲染器 |

以下结论对照代码验证过,不是推断出来的:`traceObject()` 是 `express`、`hono`、`angular`、`react` 都构建在其上的捕获路径——从不会把调用方传入的 `redactionPolicy` 选项一路透传下去。Vitest 夹具(`createNarrativeTest`/`narrativeTest`)之所以在上表里单独占一行,是因为它是一个独立的入口——一个 `NarrativeContext` 的提供者,而不是它自己的一条捕获路径——所以它的脱敏保证取决于测试内部包装时用的是哪种捕获机制(通常是 `traceObject()`,在 NestJS 测试里有时是 `AutoProxyModule`),而不是它自己的第三种行为。**`@narrativetrace/nestjs` 的 `AutoProxyModule` 是一条独立的、手写的捕获路径(`wrapPrototypeMethods`),不是 `traceObject()` 之上的一层包装**——它直接修改每个被自动包装 provider 的 prototype,而不是代理一个实例,因为 NestJS 需要它的 DI 容器创建出的每一个实例都被追踪,而不是手工包装的某一个对象。这两条路径共享 `@notTraced` 装饰器的存储(正是为此才把它挪到了 `@narrativetrace/core` 里),但不共享被捕获参数的*名字*:`wrapPrototypeMethods` 没有装饰器/反射元数据可以从一个原始的 prototype 方法里还原出参数的真实名字,所以在那里每个参数都渲染成 `arg0`、`arg1`……,而始终开启的「按名称」拒绝列表永远匹配不上这样的名字。**这是一个结构性的限制,不是以后可以修的 bug:** JavaScript 在运行时就不会暴露参数名,除非有 `@traced` 那样的元数据,而自动包装路径没有这种元数据。`@notTraced(i)`(按索引脱敏)以及基于值形状的脱敏(JWT、通过 Luhn 校验的卡号、`Set-Cookie` 字符串、或者国民身份校验位/结构规则——都与名字无关)依然能保护一个被 NestJS 自动包装的参数;仅靠基于名称的这一半轴做不到。`redactionPolicy` 选项只存在于底层的渲染函数上(`@narrativetrace/core` 里的 `renderValue`/`renderStructured`),而没有任何一个随包发布的集成暴露过覆盖它的办法。到达 `RedactionPolicy.DISABLED` 的唯一办法,是应用代码直接调用这些函数——这是你自己源码里一个刻意的、可审查的行为,而不是部署时可能被翻转的配置开关或环境变量。

## 什么会脱敏,以及谁压过谁

每一个被捕获/渲染的值,都会受到三种彼此独立的机制作用:

1. **方法参数上按索引脱敏的 `@notTraced(i)`**——在 `traceObject()` 下,*调用方*(它的值映射构建器)会在任何叙述/错误模板被解析之前,就把值替换成 `[REDACTED]` 标记,所以模板解析器在这一环节上从未真正持有过这个秘密值。在 NestJS 的 `AutoProxyModule` 下没有叙述/模板这个界面需要保护(那个集成不会读取 `@narrated`/`@onError`),但同一个装饰器依然会对被捕获的参数本身脱敏,读取的是与 `traceObject()` 相同的存储(见上文逐个界面的说明)。
2. **类上的 `static notTraced = [...]`**——针对对象内省和 `{param.property}` 模板路径的字段名脱敏。这项检查与当前生效的是哪个 `RedactionPolicy` 无关:「这个成员是否被显式标注过」这个答案是直接从类本身算出来的,然后按 `annotated || nameMatchesDenyList` 的方式组合,所以即便是在一个把所有名称模式和值形状检查都关掉的策略下,显式标注依然会脱敏。
3. **基于名称的拒绝列表**(`RedactionPolicy.DEFAULT`)——把字段名**和参数名**与一份不区分大小写、不区分重音的子串集合(`password`、`secret`、`token`、`apikey`、`cvv`、`ssn`、`authorization`、`credential`、`cardnumber`、`jwt`、`cookie`、`sessionid`、`accountnumber`、`routingnumber`、`passphrase`、`bearer`、`accesskey`、`socialsecurity`、`taxid`、`pan`、`iban`,以及它们对应的 `snake_case` 写法)进行匹配,再加上对值本身*形状*的第二重独立检查——是不是 JWT(`eyJ…`)、是不是符合 Luhn 校验的卡号、是不是一个 `Set-Cookie` 形状的字符串,或者是不是一个国民身份校验位或结构规则(智利 RUT、巴西 CPF/CNPJ、西班牙 DNI/NIE、法国 NIR、中国居民身份证,或者一个带连字符的美国社会安全号码 `AAA-GG-SSSS`——唯一没有校验位的例外,用 SSA 自己从未签发过的地区/组别/序列号段来代替)——这样一来,一个没有名字的值(列表里的一项、map 里的一个值),或者一个挂在未识别名称下的持有者令牌,依然会被捕获。**这条轴里“按参数名匹配”的这一半,只在 `traceObject()` 下生效**——一个仅仅是*名字*长得像秘密的参数(`paymentToken`、`password`)不需要任何装饰器就会被脱敏,和字段名的处理方式完全一样。在 NestJS 的 `AutoProxyModule` 下,每个参数都被捕获成 `arg0`、`arg1`……(见上文逐个界面的说明),所以这一半轴根本够不到它——在那里只有 `@notTraced` 和值形状检查还能起作用。默认词汇表是**多语言的,并且始终开启**(家族标准,与 NarrativeTrace 的其他运行时一致):西班牙语(`contraseña`、`tarjeta`、`cédula`、`claveAcceso`、`rut`、`cuit`、`dni`)、葡萄牙语(`senha`、`cartão`、`cpf`、`cnpj`)、法语(`motDePasse`、`carteBancaire`、`nir`)、德语(`passwort`、`kennwort`)和中文(`密码`、`身份证`,以及无 CJK 标识符的代码库会写的拼音 `mima`/`shenfenzheng`)与英语模式并列,无需选择任何区域设置——带重音和不带重音的拼写会折叠成同一个模式。`"companyName"`/`"panelId"` 不会匹配 `pan`——最容易产生误报的那批模式(`pan`、`iban`、`otp`、`rut`、`cuit`、`dni`、`senha`、`cpf`、`cnpj`、`nir`、`mima`)只在标识符词边界上匹配,而不是裸子串匹配,因此 `truthValue`、`circuitBreaker`、`chosenHash`、`semiMajorAxis` 和 `carbonFootprintId` 保持可见,而 `rutCliente`、`senhaUsuario` 和 `otpCode` 会被隐藏。

**自定义的 `toString()` 只有在叶子节点上才会被信任**——也就是一个完全没有自有字段的对象,这样字段内省压根没有别的东西可以展示(家族级不变量,2026-09-11;这个移植版本的设计其实早就和 .NET 一致)。*(since 0.1.3, unreleased)*一旦一个对象哪怕只有一个自有字段,它就会*始终*被逐字段内省,不管它的 `toString()` 本来会打印出什么——不只是当那个字段本身被标注或落在拒绝列表里的时候才这样。这比听起来需要的还要严格,而且是刻意为之:更早、更窄的那条规则(「除非*这个对象自己*的某个字段是脱敏目标,否则信任 `toString()`」)漏掉了 2026-09-11 这次安全修复所堵上的那种情形——一个 `toString()` 把**嵌套**对象自己精心编写的文本插值进来(`Order.toString()` 打印 `this.customer`,而 `this.customer` 本身是一个隐藏着某个字段的 `Customer`),被脱敏字段的名字或注解从来不会出现在 `Order` 自己身上,所以「自有字段」检查根本找不到任何可抓的东西,嵌套的秘密就被完整打印了出来。只在叶子节点信任 `toString()`,一次性堵上了整一类这样的绕过,不管嵌套多深都一样,而不是每出现一种新的插值形态就单独修一次。同样的规则也适用于 `Map` 的**键**:一个本身就是对象的键,会经过和值完全一样的、带脱敏意识的渲染,绝不会走一个原始的、无条件的 `toString()`。*(since 0.1.3, unreleased)*

`narrativeSummary()` 是作者专门为这条 trace 精心写的文本,依然会压过对 `toString()` 的信任和字段内省——但它并不能豁免值形状扫描(哪怕是在精心写的文本里面,JWT/PAN/SSN/国民身份/`Set-Cookie` 这样的形状也会被脱敏),而且一个会抛异常的 `narrativeSummary()` 不会再退回到 `toString()`/字段内省:整个值会直接降级成带类型的错误标记(见下文)——因为这种退回,正是一个本来是为了隐藏秘密而写的 summary,一旦自己出问题,反而会通过这个类的普通字段把秘密重新暴露出来的方式。

模板解析同样没有绕开这一切的捷径:已经审计过,确保它不会在安全渲染因为无关原因(字段/深度上限触发的截断)而恰好省略了标记时,退回去使用值的原始 `toString()`——每一个非标量的占位符值,都无条件地经过与追踪其余部分相同的、执行字段级脱敏的渲染器。

## 渲染过程中的错误

这个库在渲染一个值时会调用的成员——`narrativeSummary()`、叶子节点的 `toString()`,或者一个字段 getter——可能会抛出异常,或者(仅限 `toString()`)返回 `null`。*(since 0.1.3, unreleased)* 抛出异常时,只会把那一部分降级成带类型的错误标记 `<error: 构造函数名>`(例如 `<error: TypeError>`;抛出的不是 `Error` 的值,会显示它的 `typeof`,例如 `<error: string>`)——**绝不会显示异常的 `message`**,因为 message 里可能携带着那个成员本来拒绝渲染的确切值。一个抛异常的字段 getter,只会让那一个字段降级;其余的同级字段照常正常渲染。一个返回 `null`(而不是抛出异常)的 `toString()`,则会显示简单的 `<构造函数名>` 标记,因为并没有任何东西真的失败。

脱敏还**能在嵌套结构中存活**——一个被脱敏的成员,不管是在数组、`Set`、`Map`、普通对象里,还是这些结构层层叠加,乃至一个自引用的循环里,都由测试固定住了这一行为(`redacted-value-containment.test.ts`)。它还**会压过点名它的叙述模板**:`@narrated`/`@onError` 里的 `{param.property}` 在解析到一个指向被脱敏成员的路径时,结果始终是 `[REDACTED]`,绝不是字面值——这一点通过真实的捕获路径端到端地固定住了,特别包括「整对象占位符、默认字段转储」这种情形(对象本身完全没有自定义的 `toString()`)。

完整细节与实例见[装饰器指南 § `@notTraced`](装饰器指南.md#nottraced)。

## 保证

- **追踪失败与宿主执行是隔离的。** 捕获在设计上就是尽力而为的:解析名称、渲染参数或进入一个 span 时发生的任何失败,都会降级为一次未被追踪的调用,而绝不会阻塞或让业务方法失败(这是 `trace-object.ts` 自己的「不投毒契约」)。一个会抛异常的自定义 `toString()`、一个在模板里被点名的抛异常 getter,或者一个已满的缓冲区,都不会改变你的方法返回什么或抛出什么。
- **每一个随包发布的集成都遵守脱敏规则。** 见上面的表格——没有任何一个集成暴露过绕开它的办法。
- **带缓冲的分析路径可能会丢弃事件,但它总会报告丢失。** 它绝不会阻塞调用方,也绝不会超出自己的容量上限(一个固定大小的环形缓冲区,在 Vitest 夹具里默认是 `8,192` 个事件,在长期运行的进程里更高——见[配置指南 § 8](配置指南.md#8-事件管道缓冲bufferedeventconsumer))。一次丢过事件的捕获,会在自己的 footer 里打印丢失的数量,以及应该把容量提高到多少。

## 不做的承诺

- **没有「零开销」这种说法。** 追踪确实做了工作,而工作是有代价的——见 [README 的性能小节](../../自述文件.md#性能)。
- **不追踪私有字段,但也没有接口要求。** `#private` 类字段完全无法被 `Proxy` 拦截——这是 JavaScript 语言本身的限制。与 JVM 的动态代理不同,这里不需要先实现某个接口;任何能通过属性查找到达的方法——不管是声明在对象本身上,还是从其原型链继承来的——对 `traceObject()` 来说都是可见的。
- **目前还没有不携带值的结构化产物。** 其他一些 NarrativeTrace 实现也提供一种 `.nt` 风格的产物,完全不含运行时的值,可以交给 AI 工具使用,在结构上就不存在提示注入面。这个实现还没有构建出这个东西——见[应提交的内容](应提交的内容.md#为什么这里还没有-approvednt-这一行)。在它出现之前,这个实现生成的每一份产物都携带真实的捕获值,应当按此对待。
- **没有零代码、「包装一个你没写过的应用」这条路。** 这个平台上没有 Java agent 那样的等价物,所以范围划定始终要靠显式的调用点或类注解——见[选择集成方式 § 平台上限](选择集成方式.md#平台上限)。

## 这一页没有涵盖的内容

当 NarrativeTrace 与另一个同样包装了相同对象的库——一个 DI 容器、另一个 `Proxy`、一个契约库——叠加使用时会发生什么。简单来说:NarrativeTrace 只叙述业务边界的跨越,而哪一层包装器处在「更外层」,永远不会改变被脱敏的值、业务结果,或是最终进入叙述的异常——完整的共存契约见 [README 的 FAQ](../../自述文件.md#narrativetrace-如何与其他包装方法的库aop代理契约库交互)。
