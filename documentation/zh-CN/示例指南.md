# 示例指南

[English](../examples-guide.md) | [Español](../es/guia-de-ejemplos.md) | [Português](../pt-BR/guia-de-exemplos.md) | **简体中文**

NarrativeTrace 在 `examples/` 目录下提供了 12 个可运行的示例。每个示例都是一个独立的包，拥有自己的测试。其中四个——ecommerce、clarity、minecraft（两个版本）和 plain-js——还可以通过 `pnpm demo` 启动器访问，相关说明见[下文](#演示启动器)。

## 快速参考

| 示例 | 演示内容 | 运行命令 |
|---|---|---|
| [ecommerce](#ecommerce) | 旗舰示例：在一个已追踪的服务关系图上运行六个场景——成功、失败、一个不稳定的装饰器、fork/join | `pnpm run example:ecommerce` |
| [clarity](#clarity) | clarity 分析器所奖励和惩罚的内容：一个处于四个命名层级的酒店领域，以及报告 | `pnpm run example:clarity` |
| [express](#express) | Express 中间件 + HTTP 追踪上下文 | `pnpm run example:express` |
| [hono](#hono) | Hono 中间件 + HTTP 追踪上下文 | `pnpm run example:hono` |
| [distributed](#distributed) | 5 个微服务 + Jaeger + OTel 关联 | `pnpm run example:distributed` |
| [minecraft](#minecraft) | 领域驱动命名、追踪可读性 | `pnpm run example:minecraft` |

## 演示启动器

`pnpm demo` 是观看这些示例最快的方式：一条命令，实时叙事按调用深度着色并缩进，每种渲染都作为独立的小节公布。它会打开一个交互式选择器；`--example <name>` 以非交互方式运行；`--list` 会列出所有示例。请先构建一次（`pnpm run build`）——这些示例导入的是各个包的 `dist`。

```bash
pnpm demo                                     # 选择器：ecommerce、clarity、minecraft、plain-js
pnpm demo -- --example ecommerce              # 非交互模式
pnpm demo -- --example ecommerce --classic    # 通过 winston 桥接输出带时间戳的日志
pnpm demo -- --example ecommerce --no-pause   # 直接连续播放，没有停顿点
pnpm demo -- --example ecommerce --lang es    # 通过 examples/ecommerce/glossary.json 重新渲染这次运行
pnpm demo -- --list
```

**它是一步步走的，不是滚动播放的。** 在终端中，演示会在每个场景结束后停下——`[Enter]` 继续，`q` 退出——每个场景开场都会给出一条说明，解释*该场景的追踪是如何配置的*：这里是 `@traced`/`@narrated`/`@onError`/`@notTraced`，那里是一个带 `paramNames` 映射的裸 `traceObject`，并发的那个用的是 `ForkJoinGroup`。这些说明就写在每个示例 `src/scenarios.ts` 里紧挨着代码的地方（`Scenario { title, wiring, run }`），如果某个场景丢失了说明，或者注册表与 `--list` 的结果不一致，根测试 `tools/__tests__/demo-wiring.test.ts` 就会失败。有节奏的运行是先录制、再回放的，所以停顿点永远不会拉长追踪树报告的耗时；`--no-pause` 会直接连续、实时地播放整个运行，这也是管道和 CI 得到的方式。`NO_COLOR` 会去掉颜色，`FORCE_COLOR` 会在管道中保留颜色。

**渲染结果从何而来**这个问题，每次运行只在第一个渲染小节里回答一次。没有默认渲染器，也没有什么需要配置：捕获会产生一棵 `TraceTree`，你自己调用想要的渲染器——`renderIndentedText(tree)`、`renderProse`、`renderMermaidSequence`、`renderPlantUmlSequence`。实时的 `→ ← !!` 那几行根本不是渲染器：那是示例 `DualPathPipeline`（`tools/demo-stream.ts`，是 Java `Slf4jTraceEventListener` 的对应物）内联路径上的一个 `EventConsumer`——是唯一不需要任何渲染代码的视图。配置只在一个地方选择渲染器，也就是测试写出的追踪文件：`NARRATIVETRACE_OUTPUT=true` 加上 `NARRATIVETRACE_FORMAT=md|mmd|json|puml`。

**经典日志输出是一等公民模式。** `--classic` 会把同一次运行通过 `@narrativetrace/winston` 发送出去，采用传统的 `yyyy-MM-dd HH:mm:ss.SSS LEVEL [thread] [logger] - message` 格式——要点在于，这份叙事就是每个日志工具都能摄取的普通日志行。

**翻译后的追踪同样是一等公民模式。** 每个启动器示例都提交了一份领域词汇表（`examples/<name>/glossary.json`——一个限界上下文，附带精心整理的西班牙语和简体中文术语），`--lang es`（或 `zh-CN`）会通过它重新渲染同一次运行：标识符会以所选语言呈现，原文保留在方括号中（`buscar cliente [findCustomer]`），而参数值、返回值和错误消息则逐字节保持不变。选择器只会提供词汇表*和*库自带脚手架包二者都支持的语言区域。未翻译的短语会收集到一个"词汇表缺口"页脚——也就是有待整理的工作队列——而那些命名糟糕的场景（minecraft 未重构的那一半、clarity 的遗留处理）则故意保持未翻译：讲不出故事的名字，也没法翻译成一个故事。`@narrated`/`@onError` 模板已经在词汇表里，但尚未翻译（导出 schema 目前还不携带模板）。

启动器代码：`tools/demo.ts`（终端绑定）、`tools/demo-runner.ts`（编排逻辑，针对一个伪终端测试）、`tools/demo-args.ts`、`tools/demo-colors.ts`、`tools/demo-stream.ts`、`tools/demo-registry.ts`、`tools/demo-translate.ts`。除工作区之外零运行时依赖；从仓库根目录运行。

## Ecommerce

旗舰示例。五个内存服务（customer、catalog、inventory、payment、notification）都用 `traceObject()` 包装；真正有意思的编排逻辑在 `DefaultOrderService` 里。参数名来自 `@traced`，`placeOrder` 上的叙事来自 `@narrated`，方括号里的失败文本来自 `@onError`，卡片令牌之所以打印成 `[REDACTED]` 是因为 `@notTraced(2)`。`src/scenarios.ts` 运行 Java 的六个场景，每个场景都会打印 `--- Trace tree ---`、`--- Prose ---` 和 `--- Mermaid ---`（或 PlantUML）：

1. **成功下单 + 异步通知**——快乐路径；被 await 的通知落在了同一条追踪中，因为 `AsyncNarrativeContext` 会跨越 `await` 传递 span。
2. **支付失败——库存泄漏 bug**——追踪显示 `InventoryService.reserve` 被调用了，但 `release` 从未被调用：追踪揭示了一个真实的 bug。
3. **不稳定的外部服务**——装饰了一个桩对象的 `FlakyNotificationService` 会成功一次，然后抛出 `ExternalServiceError`；在调用点用裸 `traceObject` 包装。
4. **未知客户**——输入校验失败分支。
5. **缺货**——业务规则失败分支，额外渲染为 PlantUML。
6. **显式异步捕获**——`ForkJoinGroup.all` 对两个并发的 `RemoteCatalogService` 查询进行汇合，合并成一个 `⑂ fork` 分段。

```bash
pnpm run example:ecommerce      # 所有场景，只有小节（启动器会额外加上实时流）
pnpm demo -- --example ecommerce
```

**关键文件：**
- `examples/ecommerce/src/scenarios.ts`——场景注册表，附带接线说明
- `examples/ecommerce/src/scenario.ts`——`Scenario`/`ScenarioContext` 以及 `createDemoContext(listener)`
- `examples/ecommerce/src/traced-services.ts`——`createTracedServices()` 工厂函数
- `examples/ecommerce/src/order-service.ts`——调用其他所有服务的编排者
- `examples/ecommerce/glossary.json`——`--lang` 借以翻译的限界上下文

## Clarity

对应 Java 的 `ClarityDemoExample`：一个处于四个命名质量层级的酒店预订领域，随后是针对这四棵已捕获追踪树的 clarity 报告。各层级之间的接线完全相同——被测试的变量是命名，而不是配置。

1. **客人预订房间**——出色的、特定领域的命名（`DefaultReservationService`）。
2. **通过经理预订**——尚可但表达力较弱的命名（`DefaultBookingManager`）。
3. **遗留数据处理**——刻意设计得很弱的命名（`DefaultDataProcessor`）。
4. **客人仓储操作**——一处内聚性不匹配（查找、报告渲染和邮件发送都挤在同一个仓储里）。
5. **Clarity 分析报告**——对捕获的追踪树运行 `analyzeClarity`，用 `renderClarityReport` 和 `renderClaritySuiteReport` 打印出来。

```bash
pnpm run example:clarity
pnpm demo -- --example clarity
```

**关键文件：**
- `examples/clarity/src/scenarios.ts`——`createClarityScenarios()`；报告场景读取的是前四个场景捕获的追踪树
- `examples/clarity/src/reservation-service.ts`——命名良好的那一层级

## Express

一个 Express HTTP 服务器，用 `narrativeTrace()` 中间件包装了 ecommerce 服务。每个请求都会通过 `AsyncNarrativeContext` 获得自己的追踪上下文。

```bash
pnpm run example:express
```

然后在浏览器中打开 `http://localhost:3000`。提交订单表单——JSON 响应中既包含订单结果，也包含完整的追踪树。

**关键文件：**
- `examples/express/src/app.ts`——带有 `narrativeTrace(ctx)` 中间件的 Express 应用

## Distributed

五个运行在 Docker 容器中的微服务，通过 HTTP 相连，并借助 OpenTelemetry 和 Jaeger 实现分布式追踪关联。

**架构：**

```
浏览器 → Gateway (:3000) → Customer-Catalog (:3001)
                          → Inventory (:3002)
                          → Payment (:3003) → Fraud (:3004)
```

所有服务都通过 W3C `traceparent` 请求头传播共享同一个 `traceId`。每个服务都会同时产出 NarrativeTrace 方法级追踪和 OTel span。

### 前置条件

- Docker 和 Docker Compose

### 运行

```bash
pnpm run example:distributed
```

这会启动 6 个容器：

| 容器 | 作用 | 暴露端口 |
|---|---|---|
| jaeger | 追踪收集器 + UI | `localhost:16686` |
| gateway | API 网关，编排下单流程 | `localhost:3000` |
| customer-catalog | 客户 + 商品查询 | 内部 |
| inventory | 库存预留 | 内部 |
| payment | 支付处理，调用 fraud | 内部 |
| fraud | 欺诈评估 | 内部 |

### 下单

在浏览器中打开 `http://localhost:3000`。提交带有客户、商品和数量的订单表单。

JSON 响应包含：
- `order`——订单结果（totalCharged、transactionId）
- `trace`——从网关视角看到的 NarrativeTrace 追踪树

### 在 Jaeger 中查看追踪

打开 `http://localhost:16686`。从下拉菜单中选择一个服务（例如 `api-gateway`），然后点击 **Find Traces**。点击某条追踪即可查看跨全部 5 个服务的完整分布式 span 树。

**试试这些场景：**
- **C1 + P1**——快乐路径，所有服务都成功
- **C3 + P1**——支付被拒绝（Charlie 在黑名单中），追踪显示错误通过 payment → gateway 传播
- **Any + P2 qty 999**——库存不足，inventory 服务拒绝该预留请求

### 停止

```bash
docker compose -f examples/distributed/src/docker-compose.yml down
```

**关键文件：**
- `examples/distributed/src/gateway-app.ts`——编排对下游服务的调用
- `examples/distributed/src/traced-service-factory.ts`——创建集成了 OTel 的追踪上下文
- `examples/distributed/src/docker-compose.yml`——容器定义

## Minecraft

一个受 Minecraft 启发的领域（世界生成器、玩家物品栏、合成台、生物生成器、世界服务器），采用描述性的、领域驱动的命名。这份追踪读起来就像文档一样。

```bash
pnpm run example:minecraft
```

**输出：**
```
WorldServer.playerJoined(playerName: "Steve")
  WorldGenerator.generateChunk(x: 0, z: 0) -> {"x": 0, "z": 0, "biome": "plains", ...}
  PlayerInventory.addItem(item: {"name": "oak_log", ...}, quantity: 4) -> true
  CraftingTable.craft(recipe: {"name": "oak_planks", ...}) -> {"name": "oak_planks", ...}
  CreatureSpawner.spawnHostile(type: "zombie", x: 10, y: 64, z: 10) -> ...
-> "Steve joined the world in plains biome"
```

## Minecraft-Generic

与 minecraft 示例逻辑完全相同，但使用通用、含义不明的命名（GameManager、DataProcessor、StateManager、ThingFactory、EntityHandler）。并排比较这两份追踪——命名质量的差异立刻就能看出来。这正是 NarrativeTrace 的核心论点：如果你的追踪读不懂，需要重命名的是你的代码，而不是加更多日志语句。

```bash
pnpm run example:minecraft-generic
pnpm demo -- --example minecraft     # 两个版本都有，先是重构后的那版，与 Java 的示例一致
```

两个版本的接线方式逐字节相同——`traceObject(impl, context, paramNames, { className })`，不使用装饰器——所以真正为参数命名的是 `paramNames` 映射。

## Plain-JS

这个平台上对应 Java 的 Kotlin `library` 示例：一个纯 JavaScript 的 ESM 消费者（`.mjs`、由 `tsc --checkJs` 检查的 JSDoc 类型、不使用装饰器、不使用 TypeScript），通过带 `paramNames` 映射的 `traceObject` 追踪一个小型的图书借阅领域（`CatalogService`、`MemberService`、`LendingService`）。两个场景：一次成功的借阅（追踪树、Prose、Mermaid）和一次 `BookUnavailableError` 失败。

```bash
pnpm run example:plain-js
pnpm demo -- --example plain-js
```

**关键文件：**
- `examples/plain-js/src/scenarios.mjs`——注册表，`createTracedLendingService(context)`
- `examples/plain-js/src/lending-service.mjs`——接受一个可注入的时钟，使测试可复现

## 浏览器

一个由 Vite 提供服务的真实浏览器页面。它使用 `SyncNarrativeContext`（浏览器中没有 `AsyncLocalStorage`）以及 `@narrativetrace/core-web` 提供的 Web Crypto id 生成器。点击 **Run traced calculation** 会用 `traceObject()` 包装一个 `Calculator`，其中包括一次被捕获的 `divide(1, 0)`，让 `✗` 结果可见，随后：

- 用 `renderIndentedText` 把追踪渲染到页面中，
- 用 `renderToConsole` 把它镜像到 DevTools 控制台，
- 用 `postToCollector` 将其以 JSON 形式 POST 到 `/traces`——这是 `vite.config.ts` 中一个仅用于开发的收集器中间件，会把每条收到的追踪记录到终端。页面会报告结果（accepted / rejected / unreachable）。

```bash
pnpm run example:browser      # Vite 开发服务器，地址为 http://localhost:5175
```

测试在 jsdom 下使用 `core-web`（绝不使用 `core-node`）运行，因此这套测试练的是浏览器平台路径；`pnpm --filter @narrativetrace/example-browser build` 会做类型检查，并用 `vite build` 生成一个生产环境构建包。

**关键文件：**
- `examples/browser/index.html`——页面；加载 `src/app.ts`
- `examples/browser/src/app.ts`——入口：导入 `@narrativetrace/core-web`，挂载演示
- `examples/browser/src/demo.ts`——`mountDemo()`：追踪、页内 + 控制台渲染、收集器导出
- `examples/browser/src/calculator.ts`——被追踪的类
- `examples/browser/vite.config.ts`——开发服务器 + `/traces` 收集器中间件

## Script 标签

[plain-js](#plain-js) 的浏览器对应版本：网页中的纯 JavaScript，**没有 TypeScript、没有打包工具、没有 ES 模块**。`public/index.html` 按顺序加载两个经典 script：`/narrativetrace.global.js`——即 [`@narrativetrace/standalone`](../../packages/standalone/README.md) 打包产物，它定义了 `window.NarrativeTrace` 并注册了浏览器 id 生成器——以及 `/app.js`，手写的 ES5 风格 JavaScript（构造函数 + 原型方法；`traceObject` 并不关心对象是怎么构建出来的）。点击 **Run traced checkout** 会追踪一个 `ShoppingCart`，其中包括一次被捕获的 `checkout("EXPIRED")`，让 `✗` 结果可见，随后把追踪渲染到页面中，镜像到 DevTools 控制台，并 POST 到 `/traces`。

一个约 60 行的 `node:http` 服务器（`src/server.ts`）通过一张显式的路由表（不做目录遍历）提供这三个文件，并对 `POST /traces` 返回 202，同时记录 `[collector] received trace (N bytes)`；对 `/traces` 使用其他任何方法都会返回 405，其余路径一律 404。

```bash
pnpm run example:script-tag      # http://localhost:5176
```

测试：针对一个临时端口测试服务器本身（路由、内容类型、收集器、405/404、路径穿越），以及在 jsdom 下测试 `app.js` 本身——按浏览器的方式加载（先是 HTML body，然后是那两个经典 script）——断言四行渲染出的追踪文本，以及 accepted / rejected / unreachable 这几种收集器状态。

**关键文件：**
- `examples/script-tag/public/index.html`——页面；通过 HTML 注释自我说明
- `examples/script-tag/public/app.js`——纯 JavaScript 应用
- `examples/script-tag/src/server.ts`——静态路由 + `/traces` 收集器；由 `src/entry.ts` 启动

## Angular + Express

全栈示例：Angular 前端调用 Express ecommerce 后端，实现端到端的追踪关联。

演示了 `@narrativetrace/angular` 的全部特性：
- `provideNarrativeTrace()`——一次调用完成设置，自动带上 `traceparent` 请求头
- `provideTraced(OrderService)`——通过 Angular DI 实现零代码服务追踪
- `TraceCaptureService`——在每次下单后捕获客户端追踪
- `traceInterceptor`——自动为每个 `HttpClient` 请求添加 W3C `traceparent` 请求头

### 运行

```bash
pnpm run example:express-angular
```

这会在 `:3000` 启动 Express 后端，并在 `:4200` 启动 Vite 开发服务器。打开 `http://localhost:4200`。

下一个订单，你会看到：
- **订单结果**——orderId、transactionId、totalCharged
- **客户端追踪**——Angular 端的追踪，显示 `OrderService.placeOrder`（通过 `provideTraced`）
- **服务端追踪**——Express 端的追踪，显示 CustomerService、CatalogService、InventoryService、PaymentService
- **追踪 ID**——两端相同的 32 位十六进制 ID（traceparent 关联）

**关键文件：**
- `examples/express-angular/client/app.config.ts`——`provideNarrativeTrace()` + `provideTraced(OrderService)` 的设置
- `examples/express-angular/client/order.service.ts`——`HttpClient` 包装器，自动追踪
- `examples/express-angular/client/order-form.component.ts`——表单 UI + 追踪展示
- `examples/express-angular/server/app.ts`——带 CORS 和 `narrativeTrace(ctx)` 中间件的 Express 后端

## NestJS + React

全栈示例：一个 NestJS 后端，通过 Nest 依赖注入以**零应用代码**追踪它的服务关系图，搭配一个追踪客户端调用的 React 前端。两端都会返回各自的追踪树，让你能端到端地看到整个请求。

演示了：
- `AutoProxyModule.forRoot(...)`——`@narrativetrace/nestjs` 模块，会自动为每个 provider（`OrdersService`、`InventoryService`、`PaymentService`）加代理，使它们的方法调用无需触碰服务体本身就能被追踪
- `NarrativeStorage`——注入到 `OrdersController` 中，为当前请求 `captureTrace()`
- 客户端的 `@narrativetrace/react`——`NarrativeTraceProvider`、`useTraced()`（包装 `OrderService`）、`useTracedFetch()`，以及用于客户端追踪的 `useTraceCapture()`

### 运行

该示例没有根级别的 `example:` 脚本；要通过该包自己 `package.json` 里的脚本，用 `pnpm --filter` 运行：

```bash
# 同时启动 NestJS 服务器和 Vite 开发服务器
pnpm --filter @narrativetrace/example-nestjs-react start

# ……或者分别独立启动
pnpm --filter @narrativetrace/example-nestjs-react start:server   # NestJS，监听 :3000
pnpm --filter @narrativetrace/example-nestjs-react start:client   # Vite 开发服务器，监听 :5173
```

NestJS 后端监听 `:3000`（可用 `PORT` 覆盖），Vite 开发服务器监听 `:5173`，并将 `/orders` 代理到后端。打开 `http://localhost:5173`。

下一个订单，你会看到：
- **订单结果**——orderId（`ORD-*`）、transactionId（`TXN-*`）、totalCharged
- **客户端追踪**——React 端 `OrderService.placeOrder` 的追踪（通过 `useTraced`）
- **服务端追踪**——NestJS 端 `OrdersService` → `InventoryService` / `PaymentService` 的追踪，由 DI 自动代理

### 测试

```bash
pnpm --filter @narrativetrace/example-nestjs-react test
```

**关键文件：**
- `examples/nestjs-react/server/app.module.ts`——`AutoProxyModule.forRoot(...)` 接线
- `examples/nestjs-react/server/orders.controller.ts`——通过注入的 `NarrativeStorage` 捕获请求追踪
- `examples/nestjs-react/server/orders.service.ts`——编排者（`InventoryService` + `PaymentService`）
- `examples/nestjs-react/client/order-form.tsx`——`useTraced` / `useTracedFetch` / `useTraceCapture` + 追踪展示

## 运行所有示例

```bash
pnpm run example:all
```

依次运行 ecommerce、minecraft、minecraft-generic、clarity 和 plain-js，然后并行启动 express 和 hono。distributed 示例需要 Docker，单独运行。若想要有引导、有节奏的导览，请改用 `pnpm demo`。

## 运行测试

每个示例都有自己的测试套件：

```bash
cd examples/ecommerce && pnpm run test      # 51 个测试（领域 + 追踪 + 六个场景）
cd examples/clarity && pnpm run test        # 8 个测试（领域 + 各层级 + 报告）
cd examples/express && pnpm run test         # 4 个测试
cd examples/hono && pnpm run test            # 5 个测试
cd examples/distributed && pnpm run test     # 40 个测试
cd examples/minecraft && pnpm run test       # 22 个测试（领域 + 追踪集成）
cd examples/minecraft-generic && pnpm run test  # 18 个测试
cd examples/plain-js && pnpm run test        # 8 个测试（带 JSDoc 类型的 .mjs）
cd examples/browser && pnpm run test         # 4 个测试
cd examples/express-angular && pnpm run test # 16 个测试（服务端 + Angular 组件和服务）
cd examples/nestjs-react && pnpm run test    # 13 个测试（NestJS supertest + React 组件和服务）

# 或者通过 turbo 一次性运行全部：
pnpm run test

# 启动器自身的测试（解析器、着色器、流、注册表/接线检查、翻译、运行器）
pnpm run test:root
```
