# 应提交的内容

[English](../what-to-commit.md) | [Español](../es/que-commitear.md) | [Português](../pt-BR/o-que-commitar.md) | **简体中文**

NarrativeTrace 默认就会写出描述某一次测试运行的文件——使用 `createNarrativeTest` 的测试套件不需要配置任何东西就能拿到它们。其中大多数是生成产物,而不是经过审阅的契约。除了 `glossary.json` 之外唯一刻意存在的例外是已审批的追踪(`.approved.nt`)*(since 0.1.3, unreleased)*——通过 `approval: true` 开启它(参见[配置指南](配置指南.md#2-vitest-配置)),它就会变成一份经过审阅、手写的契约,和其他任何 NarrativeTrace 实现里的审批基线一样。

| 产物 | 要提交吗? | 原因 |
|---|---|---|
| `narrativetrace-output/**/*.md` | 不要 | 每次运行都会重新生成 |
| `narrativetrace-output/**/*.json` | 不要 | 与结构化 JSON 是同一条追踪——每次运行都会重新生成 |
| `narrativetrace-output/**/*.canonical.json` | 不要 | 带有模式版本号的规范化导出——每次运行都会重新生成 |
| `narrativetrace-output/diagrams/**/*.mmd` / `*.puml` | 不要 | 每次运行都会重新生成 |
| `narrativetrace-output/**/*.clarity-json` | 不要 | 按场景划分的清晰度分数——每次运行都会重新生成 |
| `narrativetrace-output/clarity-report.md` / `clarity-results.json` | 不要 | 整个测试套件的汇总结果(通过 `ClaritySuiteReporter` 生成)——是一份生成的报告,不是一个决定 |
| `narrativetrace-output/structural/**/*.nt` | 不要 | 控制台差异和失败报告据以比较的*本地*最近一次绿色基线——不是下面的已审批追踪 |
| `narrativetrace-output/manifest.json` | 不要 | 场景 → 产物 索引,外加本次运行自身的 `id`/`name` *(since 0.1.3, unreleased)*——每次运行都会重新生成 |
| `<approvedDir>/**/*.approved.nt` | **要** | 经过审阅的已审批追踪(只有设置了 `approval: true` 才存在)——这份列表里唯一一个刻意的决定,而非输出产物 |
| `<approvedDir>/**/*.received.nt` | 不要 | 在审批不一致时写出,或者在尚不存在已审批追踪时写出。审阅它,运行 `pnpm run approve-narratives`(或 `narrativetrace-approve`)来提升它,然后删除它或让脚本移除它——绝不要提交这份已接收的追踪本身 |
| `<approvedDir>/**/*.incomplete.nt` | 不要 | 当运行本身不完整时(有事件被丢弃,或某个异步作用域被拒绝),写出它代替 `.received.nt`——按子序列包含关系比较,永远不能被提升 |
| `glossary.json` / `glossary.md` | **要**,如果使用了术语表采集功能 | 采集完成后提交到仓库根目录;已提交的文件才是清晰度评分与词汇检查在之后每次运行时实际读取的内容——"一份文件,一套评审流程" |
| `.claude/skills/**/SKILL.md`、`.agents/skills/**/SKILL.md`、`AGENTS.md` 中的 `<!-- narrativetrace:skills:* -->` 区块 | **要** *(since 0.1.3, unreleased)* | 这是 `packages/skills` 类型化目录(`pnpm run skills-render`)的构建产物,不是测试运行的输出——和 `glossary.json` 一样提交:重新生成、在 diff 中审阅、并针对偏差进行检查(`pnpm run skills-check`,已接入 `pnpm run check`),而不是手工编辑 |

`narrativetrace-output/` 目录下的一切都是输出产物。如果你还没有这样做,请把它加入 `.gitignore`:

```gitignore
narrativetrace-output/
```

`<approvedDir>`(默认 `narratives/`)则不是:里面的 `.approved.nt` 文件本应被纳入版本控制,但放在它旁边的 `.received.nt`/`.incomplete.nt` 并不会自动被排除。请为它们添加明确的排除规则:

```gitignore
narratives/**/*.received.nt
narratives/**/*.incomplete.nt
```

如果某个 CI 任务只想要控制台叙事和清晰度/术语表元数据、不想要这些文件,可以设置
`NARRATIVETRACE_OUTPUT=false`——参见[配置指南](配置指南.md#2-vitest-配置)。

## 一句话说清这条规则

如果一个文件的存在只是因为跑了一次测试,它就是输出——不要提交它。如果一个文件的存在是因为有人审阅并接受了它,它就是一份基线——提交它,并且预期它的差异会像快照测试的差异一样在代码评审中被阅读。`glossary.json` 和 `.approved.nt` 是这份列表里两个需要人在落地前先审阅的文件:采集功能只是提出词汇表新增建议,而一次被拒绝的结构变更会写出一份已接收的追踪,但提交这两者中的任何一个都是真正的批准(参见[清晰度指南](清晰度指南.md)、[功能指南 § 改进代码](功能指南.md#改进代码清晰度诊断),以及 [Structural Trace Format](../structural-trace-format.md)(尚未翻译)以了解完整的审批流程)。
