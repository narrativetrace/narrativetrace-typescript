# 智能体技能

[English](../agent-skills.md) | [Español](../es/habilidades-de-agente.md) | [Português](../pt-BR/habilidades-de-agente.md) | **简体中文**

NarrativeTrace 提供**技能(skill)**:一种可供智能体加载的流程,它会运行经过测试的命令,并以 `verify` 步骤作为完成的判定标准——而不是一份智能体可能读、也可能不读的文档。技能在设计上刻意保持轻量:检查、诊断或生成的逻辑都放在经过测试的库代码里;技能自身的工作只是判断何时该出手、调用那些经过测试的代码,并结合上下文解读结果。

## 六个技能:准备、诊断、清晰度、报告、验证与调试

- **`add-narrative-tracing`**——把 NarrativeTrace 装进一个项目,并让它产出第一条追踪:用真实的工具链安装、运行 doctor 并依次应用它打印的每一条 `config.<framework>-*` 修复来接好项目已在使用的框架(页面上不列任何框架:已安装的 doctor 自带的框架表才是依据)、包装一个类、渲染并运行第一条追踪,然后接入一个真正的日志系统(pino/winston/OpenTelemetry)。最后运行一次 `npx @narrativetrace/cli doctor` 并把接力棒交出去——这是两个技能之间的接缝。
- **`narrativetrace-doctor`**——只负责诊断,而且是**只读的**:从不编辑、生成或删除任何文件。运行经过测试的 CLI,读取它的报告,并走完那些单靠一份 CLI 输出覆盖不到的部分:在测试里证明脱敏生效、在断言之前先阅读一份已生成的追踪、以及审批追踪流程(标记为尚未研究——它自己的评测单元仍待完成)。
- **`add-narrativetrace-clarity`**——在 Vitest 项目里添加或验证命名报告:注册来自 `@narrativetrace/vitest/reporters` 的 `ClaritySuiteReporter`,运行测试套件,检查 `clarity-results.json` 是新生成且非空的,读取分数和问题并加以解释。它按报告自己给出的建议重命名,并反复重新运行,直到 `npx narrativetrace-clarity` 通过;只有在被要求时才会往包的脚本里加一道门禁——而且绝不会调低项目已有的阈值。
- **`narrativetrace-feedback`**——报告 NarrativeTrace 自身的缺陷:doctor 的某项检查有误或其修复不起作用、某个技能步骤无法照做、安装提示词的措辞把人引向了错误的方向,或者库在配置正确的项目里行为异常。它背后经过测试的动词 `narrativetrace feedback` 会根据项目起草报告(安装坐标、doctor 自己的 JSON 报告,以及至多一份结构化追踪),并且**拒绝写出带有你的追踪中任何取值的报告**——同时点名拒绝它的规则,让你有具体的东西可改,而不是一条可以无视的警告。随后技能会展示完整的草稿,并只问一次是否公开提交。它不会向任何地方发送任何东西,没有你在自己的一轮对话里给出的回答,也不会提交任何东西。
- **`narrativetrace-verify`**——在智能体宣布完成之前,先读出一次改动实际做了什么。它在测试变绿之后运行,并以一条会明说出来的成本规则开场:跨协作者、带分支、会重试、异步运行或携带状态的改动要追踪;纯函数或只改一个类的编辑则跳过,并说明原因。接着它在运行**之前**先写下意图(拿什么都没有的东西去读追踪,只会确认无论发生了什么),运行最小的真实路径,把不含取值的结构化 `.nt` 与意图对照着读,只在一个 span 上打开取值,并报告追踪所显示的内容——每一条结论都引用一个 span id(`#1.3`)。它的最后几步会**固定**这条流程:打开审批模式、运行整个测试套件、完整展示 `.received.nt`、问一个问题,并且只有在你答应之后才提升为基线。
- **`narrativetrace-debug`**——从症状而不是从改动出发:在开启追踪的情况下复现它,在改动任何代码**之前**先按 span id 点名取值第一次出现偏差的那个 span,通过再包装一个协作者(绝不使用会脱敏的 `@notTraced`)把范围收窄到该 span 的子树,就在那个 span 里修复,检查结构化追踪显示没有其他东西发生变化,并把这次复现作为回归测试固定下来,走同一道门禁。NarrativeTrace 自身的缺陷会交给 `narrativetrace-feedback`,而不是绕过去。

这些技能可以组合使用:一个全新的项目从 `add-narrative-tracing` 开始;一个已经装好 NarrativeTrace、但哪里不对劲的项目,从 `narrativetrace-doctor` 开始。不管走哪条路,最终都会落到 doctor 这里——从此往后的诊断由它负责。`add-narrativetrace-clarity` 负责第一份命名报告和可选的清晰度强制检查;它不安装追踪,也不收集术语表,而且没有任何 doctor 发现项指向它,因为不会有什么东西因为缺少一份报告而失败。`narrativetrace-feedback` 则是当问题最终证明出在我们而不是项目身上时,一条路径的终点——doctor 自己的收尾规则就指向它。生成部分(比如今天 doctor 只能提醒你去添加的那个脱敏证明测试)会由未来的另一个技能负责。`narrativetrace-verify` 是追踪跑通之后下一次会话的起点——安装技能的最后一步会把接力棒交给它——而 `narrativetrace-debug` 则是已报告症状的起点。两者渲染同一份共享的“如何阅读追踪”小节,因此绝不会教出两种读同一个文件的方式。

## 安装方式

- **`npx @narrativetrace/cli init`**——对任何项目而言最快的路径:先预览计划和一份统一 diff(`--dry-run`,不写入任何东西),确认无误后再原样应用预览过的内容。它会把六个技能都复制到 `.agents/skills/`——如果项目属于那个供应商,也会复制到 `.claude/skills/`——并在 `AGENTS.md` 里写入一段带标记的内容;已经存在的 `CLAUDE.md` 只会新增一行 `@AGENTS.md`,不会新建任何文件。随时可以重新运行来刷新:没有构建钩子,重新运行只会重写它自己拥有的那些页面和那段内容。完整的参数说明见 [`@narrativetrace/cli`](../../packages/cli/README.md#narrativetrace-init)。针对一个空项目的预览见下文。
- **手动复制生成好的文件**仍然是备用方案——路径和 `init` 写入的完全一样,只是没有那行来源标记,也不会帮你更新 `AGENTS.md` 里的那段内容。**Claude Code**:本仓库中已有生成好的 `SKILL.md`,分别位于 [`.claude/skills/add-narrative-tracing/`](../../.claude/skills/add-narrative-tracing/SKILL.md) 、[`.claude/skills/narrativetrace-doctor/`](../../.claude/skills/narrativetrace-doctor/SKILL.md) 、[`.claude/skills/narrativetrace-feedback/`](../../.claude/skills/narrativetrace-feedback/SKILL.md) 、[`.claude/skills/add-narrativetrace-clarity/`](../../.claude/skills/add-narrativetrace-clarity/SKILL.md) 、[`.claude/skills/narrativetrace-verify/`](../../.claude/skills/narrativetrace-verify/SKILL.md) 和 [`.claude/skills/narrativetrace-debug/`](../../.claude/skills/narrativetrace-debug/SKILL.md),每个目录都以其技能的规范名称命名——Claude 插件的前缀是唯一可以合法使用缩短片段的地方,而本仓库里没有任何东西是插件。把其中任意一个目录复制到你自己项目的 `.claude/skills/<名称>/` 下,Claude 就会自动识别它,可以直接按名字(`add-narrative-tracing` / `narrativetrace-doctor` / `narrativetrace-feedback` / `add-narrativetrace-clarity` / `narrativetrace-verify` / `narrativetrace-debug`)调用。**Codex**:生成好的 `SKILL.md` 也同样存在于 [`.agents/skills/add-narrative-tracing/`](../../.agents/skills/add-narrative-tracing/SKILL.md) 、[`.agents/skills/narrativetrace-doctor/`](../../.agents/skills/narrativetrace-doctor/SKILL.md) 、[`.agents/skills/narrativetrace-feedback/`](../../.agents/skills/narrativetrace-feedback/SKILL.md) 、[`.agents/skills/add-narrativetrace-clarity/`](../../.agents/skills/add-narrativetrace-clarity/SKILL.md) 、[`.agents/skills/narrativetrace-verify/`](../../.agents/skills/narrativetrace-verify/SKILL.md) 和 [`.agents/skills/narrativetrace-debug/`](../../.agents/skills/narrativetrace-debug/SKILL.md)——这是 Codex CLI 自己会发现的布局,它从工作目录向上一路找到仓库根目录(此外还会查看 `~/.agents/skills` 里的用户级全局技能)。它的 frontmatter 是 Claude 那一份的严格子集(只有 `name` 和 `description`——没有 `when_to_use`,也没有 `allowed-tools`),所以两种布局下发布的是完全相同的页面正文。来源:developers.openai.com/codex/skills 和 developers.openai.com/codex/concepts/customization(获取于 2026-09-13)。
- **任意智能体、任意平台**:任何会读取 `AGENTS.md` 的智能体都能看到本仓库 `AGENTS.md` 自身在 `<!-- narrativetrace:skills:start -->` 标记之间携带的常驻提示——这六个技能的名字和描述,这样一个从未想过要去找它们的智能体也能知道它们的存在。
- **Gemini** 已经在路线图上,但目前还没有实现。

## 来自注册表

一个项目可以在这里的任何人都从未运行过安装器的情况下,携带这些技能,处于以下三种状态之一:

1. **由 `init` 安装的**——已提交,属于团队。这是 `config.skills-installed` 唯一会通过的状态:页面带有来源标记,并且与这个项目所解析的版本一致。
2. **来自注册表的个人安装**(一个 Claude Code 插件缓存)——只属于你自己。按设计对 doctor 不可见:它诊断的是项目,而个人安装不会触达任何队友,也不会触达任何其他智能体。
3. **安装进项目里的注册表安装**(`npx skills add`)——这是本仓库自己生成的页面,由注册表而不是 `init` 落地的,所以目前还没有来源标记。

自己试用这些技能,而不改动项目:

```text
/plugin marketplace add narrativetrace/narrativetrace-typescript
/plugin install narrativetrace-typescript@narrativetrace-typescript
```

然后运行 `npx @narrativetrace/cli init --dry-run`,阅读 diff,再不带该参数运行一次,让 `AGENTS.md` 指向它们。

从开放标准注册表安装进项目:

```text
npx skills add narrativetrace/narrativetrace-typescript
```

然后运行 `npx @narrativetrace/cli init --dry-run`,阅读 diff,再不带该参数运行一次,让 `AGENTS.md` 指向它们。

注册表留下的页面绝不会仅仅因为它存在就被拒绝。`init` 会把它和自己本应生成的内容逐字节比较,只对换行符做归一化处理。一份与本版本自身页面完全相同的页面会被**采纳(adopted)**——计划是这么说的,而不是"替换(replaced)",因为阅读它的人必须知道,没有任何属于他们的东西被覆盖。下面是计划自身的原文,照原样引用,绝不在这里重新敲一遍:

```ts
const ADOPTED = "adopted: identical to this carrier's page, so only the provenance line is added";
```

一份不同的页面——另一个版本,或是被手动编辑过的——仍然保留 `--force` 所对应的那种普通拒绝。`npx skills add` 还会把 `.claude/skills/<名称>` 留成一个指向开放标准页面的符号链接;`init` 永远不会透过这样的链接写入。一个它会采纳、或者已经拥有其目标的链接,会被替换成一个带有正确版本内容的真实目录;其他任何链接都会被拒绝,因为 `--force` 只覆盖内容,从不覆盖链接。

而下面是 doctor 自身的修复建议,同样照原样引用,针对那种页面已经存在、却完全没有这些标记的项目:

```ts
const INIT_DRY_RUN = "npx --yes @narrativetrace/cli init --dry-run";
const NOT_OURS = " (there, but not ours)";

/**
 * What a page with no provenance line most often IS: a registry install (design D5 state 3) — `npx
 * skills add`, or a plugin or workspace install — of this repository's own rendered pages. Naming the
 * case matters because the obvious reading of "not ours" is "somebody else's work", which invites a
 * `--force` nobody needs: `init` ADOPTS a page identical to this release's.
 */
const FROM_A_REGISTRY =
  " Pages that are there without our line usually came from a registry (npx skills add, a plugin" +
  " or workspace install). A page identical to this release's is adopted, and no --force is needed.";
```

## 它们是如何构建的

这些技能都从不手工编辑。`packages/skills-catalogue/src/catalogue/add-narrative-tracing.ts`、`packages/skills-catalogue/src/catalogue/narrativetrace-doctor.ts` 、`packages/skills-catalogue/src/catalogue/narrativetrace-feedback.ts` 、`packages/skills-catalogue/src/catalogue/add-narrativetrace-clarity.ts` 、`packages/skills-catalogue/src/catalogue/narrativetrace-verify.ts` 和 `packages/skills-catalogue/src/catalogue/narrativetrace-debug.ts` 是这六个技能的真相来源(后三者共用的阅读小节、审批门禁和固定步骤只写一次,放在它们旁边);`pnpm run skills-render` 会据此重新生成每个技能的 `.claude/skills/` 和 `.agents/skills/` 页面,以及本仓库自身 `AGENTS.md` 中的对应小节,而 `pnpm run skills-check`(已接入 `pnpm run check`)会在任何一份生成页面偏离类型化源头时立刻让构建失败。生成页面展示的每一段代码,都是通过本仓库其他文档同样使用的 `<!-- snippet: -->` 标记约定,从真实、经过测试的源代码中嵌入的——绝不是手工敲出来的示例。一条 A 级 lint 规则会把私有规划笔记的引用挡在这些页面之外:说明性的句子可以留下,点名那份笔记的引用不行。第二条 lint 规则守护那个以“缺席”为特性的 frontmatter 字段:凡是其步骤可能把东西公开出去的技能——如今就是 `narrativetrace-feedback`——都不得声明 `allowed-tools`,因为该字段会在加载该技能的那一轮里免提示地预先批准其列出的工具,而一个预先批准了自己报告命令的报告类技能,会让工具环境恰好在最该询问的地方不再询问。第三条 lint 规则对提升审批基线的那两个技能(`narrativetrace-verify`、`narrativetrace-debug`)守住同一条底线:运行批准命令的技能完全不声明任何允许的工具。
