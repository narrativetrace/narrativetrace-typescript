# 智能体技能

[English](../agent-skills.md) | [Español](../es/habilidades-de-agente.md) | [Português](../pt-BR/habilidades-de-agente.md) | **简体中文**

NarrativeTrace 提供**技能(skill)**:一种可供智能体加载的流程,它会运行经过测试的命令,并以 `verify` 步骤作为完成的判定标准——而不是一份智能体可能读、也可能不读的文档。技能在设计上刻意保持轻量:检查、诊断或生成的逻辑都放在经过测试的库代码里;技能自身的工作只是判断何时该出手、调用那些经过测试的代码,并结合上下文解读结果。

## 两个技能:准备与诊断

- **`add-narrative-tracing`**——把 NarrativeTrace 装进一个项目,并让它产出第一条追踪:用真实的工具链安装、包装一个类、渲染并运行第一条追踪,然后接入一个真正的日志系统(pino/winston/OpenTelemetry)。最后运行一次 `npx @narrativetrace/cli doctor` 并把接力棒交出去——这是两个技能之间的接缝。
- **`narrativetrace-doctor`**——只负责诊断,而且是**只读的**:从不编辑、生成或删除任何文件。运行经过测试的 CLI,读取它的报告,并走完那些单靠一份 CLI 输出覆盖不到的部分:在测试里证明脱敏生效、在断言之前先阅读一份已生成的追踪、以及审批追踪流程(标记为尚未研究——它自己的评测单元仍待完成)。

这两个技能可以组合使用:一个全新的项目从 `add-narrative-tracing` 开始;一个已经装好 NarrativeTrace、但哪里不对劲的项目,从 `narrativetrace-doctor` 开始。不管走哪条路,最终都会落到 doctor 这里——从此往后的诊断由它负责。生成部分(比如今天 doctor 只能提醒你去添加的那个脱敏证明测试)会由未来的另一个技能负责。

## 安装方式

- **`npx @narrativetrace/cli init`**——对任何项目而言最快的路径:先预览计划和一份统一 diff(`--dry-run`,不写入任何东西),确认无误后再原样应用预览过的内容。它会把两个技能都复制到 `.agents/skills/`——如果项目属于那个供应商,也会复制到 `.claude/skills/`——并在 `AGENTS.md` 里写入一段带标记的内容;已经存在的 `CLAUDE.md` 只会新增一行 `@AGENTS.md`,不会新建任何文件。随时可以重新运行来刷新:没有构建钩子,重新运行只会重写它自己拥有的那些页面和那段内容。完整的参数说明见 [`@narrativetrace/cli`](../../packages/cli/README.md#narrativetrace-init)。针对一个空项目的 `--dry-run --json` 预览大致是这样:
  ```json
  {
    "carrier": "@narrativetrace/skills@0.2.0",
    "actions": [
      {
        "kind": "create",
        "path": ".agents/skills/narrativetrace-doctor/SKILL.md",
        "status": "planned"
      },
      {
        "kind": "create",
        "path": ".agents/skills/add-narrative-tracing/SKILL.md",
        "status": "planned"
      },
      {
        "kind": "create",
        "path": "AGENTS.md",
        "status": "planned"
      }
    ],
    "exitCode": 0
  }
  ```
- **手动复制生成好的文件**仍然是备用方案——路径和 `init` 写入的完全一样,只是没有那行来源标记,也不会帮你更新 `AGENTS.md` 里的那段内容。**Claude Code**:本仓库中已有生成好的 `SKILL.md`,分别位于 [`.claude/skills/add-narrative-tracing/`](../../.claude/skills/add-narrative-tracing/SKILL.md) 和 [`.claude/skills/narrativetrace-doctor/`](../../.claude/skills/narrativetrace-doctor/SKILL.md),每个目录都以其技能的规范名称命名——Claude 插件的前缀是唯一可以合法使用缩短片段的地方,而本仓库里没有任何东西是插件。把其中任意一个目录复制到你自己项目的 `.claude/skills/<名称>/` 下,Claude 就会自动识别它,可以直接按名字(`add-narrative-tracing` / `narrativetrace-doctor`)调用。**Codex**:生成好的 `SKILL.md` 也同样存在于 [`.agents/skills/add-narrative-tracing/`](../../.agents/skills/add-narrative-tracing/SKILL.md) 和 [`.agents/skills/narrativetrace-doctor/`](../../.agents/skills/narrativetrace-doctor/SKILL.md)——这是 Codex CLI 自己会发现的布局,它从工作目录向上一路找到仓库根目录(此外还会查看 `~/.agents/skills` 里的用户级全局技能)。它的 frontmatter 是 Claude 那一份的严格子集(只有 `name` 和 `description`——没有 `when_to_use`,也没有 `allowed-tools`),所以两种布局下发布的是完全相同的页面正文。来源:developers.openai.com/codex/skills 和 developers.openai.com/codex/concepts/customization(获取于 2026-09-13)。
- **任意智能体、任意平台**:任何会读取 `AGENTS.md` 的智能体都能看到本仓库 `AGENTS.md` 自身在 `<!-- narrativetrace:skills:start -->` 标记之间携带的常驻提示——这两个技能的名字和描述,这样一个从未想过要去找它们的智能体也能知道它们的存在。
- **Gemini** 已经在路线图上,但目前还没有实现。

## 它们是如何构建的

这两个技能都从不手工编辑。`packages/skills-catalogue/src/catalogue/add-narrative-tracing.ts` 和 `packages/skills-catalogue/src/catalogue/narrativetrace-doctor.ts` 是这两个技能的真相来源;`pnpm run skills-render` 会据此重新生成这两个技能各自的 `.claude/skills/` 和 `.agents/skills/` 页面,以及本仓库自身 `AGENTS.md` 中的对应小节,而 `pnpm run skills-check`(已接入 `pnpm run check`)会在任何一份生成页面偏离类型化源头时立刻让构建失败。生成页面展示的每一段代码,都是通过本仓库其他文档同样使用的 `<!-- snippet: -->` 标记约定,从真实、经过测试的源代码中嵌入的——绝不是手工敲出来的示例。一条 A 级 lint 规则会把私有规划笔记的引用挡在两份页面之外:说明性的句子可以留下,点名那份笔记的引用不行。
