# NarrativeTrace TypeScript 清晰度指南

[English](../clarity-guide.md) | [Español](../es/guia-de-claridad.md) | [Português](../pt-BR/guia-de-clareza.md) | **简体中文**

如果追踪即代码,那么追踪的质量就是代码的质量。清晰度模块会分析你的方法名、类名和参数名,并对它们传达意图的效果进行评分。

## 快速开始

```ts
import { analyzeClarity, renderClarityReport } from "@narrativetrace/clarity";

const result = analyzeClarity(context.captureTrace());
console.log(renderClarityReport([{ scenario: "Order Placement", result }]));
```

在 Vitest 中,使用 `"clarity-json"` 格式时会自动生成清晰度报告——无需任何代码。

## 评分内容

清晰度由五个加权组件得出一个总体评分(0.0–1.0):

| Component | Weight | What it measures |
|---|---|---|
| 方法名 | 30% | 动词质量、token 特异性、缩写、token 数量 |
| 参数名 | 25% | 领域特异性与泛化/无意义 token 的对比 |
| 类名 | 20% | 角色后缀质量、前缀特异性 |
| 结构 | 15% | 参数数量与调用深度的扣分 |
| 内聚性 | 10% | 方法是否与类的角色后缀保持一致 |

## 评分实践

### 方法名

第一个 token 被视为动词。领域动词得分最高,泛化动词得分最低:

| 动词类别 | 示例 | 评分 |
|---|---|---|
| 领域 | `calculate`、`validate`、`reserve`、`dispatch` | 0.60 |
| 标准 | `create`、`find`、`delete`、`update` | 0.45 |
| 布尔前缀 | `is`、`has`、`can`、`contains` | 1.00 |
| 泛化 | `get`、`set`、`process`、`handle`、`execute` | 0.10 |

像 `reserveInventory` 这样的多 token 方法比像 `reserve` 这样的单 token 方法得分更高,因为额外的 token 增加了特异性。

### 类名

类名应当带有角色后缀。设计模式后缀和功能性后缀在搭配领域前缀时得分较高:

| Pattern | Score | Why |
|---|---|---|
| `OrderService` | 1.0 | 领域前缀 + 功能性后缀 |
| `Service` | 0.0 | 没有前缀——无意义 |
| `DataProcessor` | 低 | 模糊前缀 + 泛化后缀 |
| `BookingManager` | 中 | 领域前缀,但 `Manager` 是泛化后缀 |

### 参数名

领域专属命名得分高,泛化命名得分低:

| 层级 | 示例 | 评分 |
|---|---|---|
| 领域专属 | `customerId`、`checkInDate`、`roomCategory` | 0.80+ |
| 带类型的泛化 | `id`、`name`、`count`、`status` | 0.50 |
| 模糊 | `data`、`info`、`result`、`object` | 0.10 |
| 无意义 | `x`、`foo`、`val`、`temp` | 0.00 |

### 结构扣分

参数超过 4 个或调用深度超过 5 层的方法会被扣分。每超出一个参数扣 0.1;每超出一层深度扣 0.05。

### 内聚性

方法会与类的角色后缀所对应的预期动词进行比对。`Repository` 类应当拥有 `find`、`save`、`delete`、`count` 这样的方法。`GuestRepository` 上出现 `renderReport` 这样的方法会被标记为不一致。

## 问题与严重级别

清晰度方面的缺陷会作为问题报告,并按影响程度排序:

| 严重级别 | 阈值 | 示例 |
|---|---|---|
| HIGH | 评分 ≤ 0.20 | `DataProcessor.execute(data)` |
| MEDIUM | 评分 ≤ 0.50 | `BookingManager.handleBooking(name, type)` |
| LOW | 评分 > 0.50 | 少量使用缩写 |

重复的问题(类别与元素均相同)会被去重并记录出现次数。问题按影响分(严重级别权重 × 出现次数)排序。

## 你自己的词汇表,来自你已有的术语表

内置词典懂得通用的软件英语。它们不知道 `fold` 在你的领域里是一个动词,不知道 `tranche` 是一个精确的名词,也不知道 `fx` 是你团队认可的缩写——而它们不认识的名称会被评为未知,而不是领域专属。

你用仓库中已有的词汇文件来教它们:已提交的 `glossary.json`(ADR-012)。没有第二个需要同步维护的词典文件。

| 术语表条目 | 类型 | 清晰度学到了什么 |
|---|---|---|
| `settle trade` | `verb-phrase` | `settle` 是领域动词;`trade` 是领域名词 |
| `credit tranche` | `noun-phrase` | `credit` 和 `tranche` 都是领域名词 |
| `foreign exchange` | `noun-phrase` | `foreign` 和 `exchange` 都是领域名词 |

多词术语按 token 逐个施教,因为标识符本来就是按 token 逐个评分的。所有限界上下文都会贡献词汇:标识符不携带模块路径,因此评分时无法应用按上下文的作用域。

### 认可的缩写靠声明,而不是推断

缩写存在于它们自己的根级小节中(术语表 schema 2):

```json
{
  "schemaVersion": 2,
  "abbreviations": { "fx": "foreign exchange", "calc": "calculate" }
}
```

被列出的 token 就是你团队的词:缩写词典不再要求将其拼写展开,而这个展开会在被提及时用于施教。

**作为已提交术语中的一个 token,是刻意不足够的。** 采集短语 `calc total` 绝不能因此就悄悄地在整个仓库中认可 `calc`——没有人在批准该短语时读过 `calc`,而且 `calc → calculate` 这条提示会在所有地方同时消失。是否认可,是需要有人做出的决定。

这也让术语表在通用语言(ubiquitous language)方面保持诚实。若不这样做,要认可 `fx` 就必须把 `fx` 作为规范*术语*提交——但该领域的用词是 `foreign exchange`,同时保留两者会让一个概念产生两条记录,而这正是术语表存在的目的所要防止的(ADR-012)。

这一小节归人类所有:采集永远不会写入它,合并会将其原样带过,并且它会被渲染进 `glossary.md`,以便这项决定像其他决定一样接受评审。没有声明任何缩写的术语表会继续标注 `"schemaVersion": 1`,并且逐字节地按原样序列化。

### 术语表做不到的事

内置词典保留其权威性。项目可以教会评分器一个它们不认识的词;但不能推翻一个它们已经认识的词。

- **泛化动词仍然是泛化的。** 提交 `process` 或 `handle` 不会提升它们,布尔前缀(`is`、`has`)同理。
- **无意义的占位符仍然无意义。** `temp`、`foo` 之类不会因为被写下来就获得意义。
- **废弃的同义词永远不是词汇表的一部分。** 别名的存在就是为了被标记出来;将其提升会让它本该触发的 `non-canonical-term` 问题失声。
- **`stale`(过期)术语不是词汇表的一部分。** 将一个术语标记为 stale,就是在说这个词已经离开了该领域。

只有*已提交*的文件才算数。某次运行采集到的内容不会反馈到这同一次运行的评分中——一个会自我膨胀的词汇表会让评分变得不确定且自我认证。提交,就是人工批准。

### 适用范围

Vitest 夹具(fixture)会读取由 `NARRATIVETRACE_GLOSSARY_DIR` 指定的术语表(默认为工作目录),并按 worker 进程记忆化一次。读取是无条件的——这与采集不同,采集是可选启用的(`NARRATIVETRACE_GLOSSARY=true`),因为它会重写工件目录之外的文件。没有 `glossary.json` 的仓库,其评分与该功能出现之前完全一致;而无法读取的术语表会带着一条警告降级为仅使用内置词典,而不会使测试套件失败。

```ts
import { analyzeClarity } from "@narrativetrace/clarity";
import { projectVocabulary } from "@narrativetrace/vitest";

// 在夹具之外手动评分:
const result = analyzeClarity(tree, projectVocabulary());
```

`@narrativetrace/glossary` 直接暴露了这份映射本身——面向已解析术语表的 `glossaryVocabulary(glossary)`,以及面向磁盘上术语表的 `readProjectVocabulary(dir, fileReader)`——这样非 Node 宿主环境也能提供自己的文件访问方式。

## 报告输出

### 单个场景

```ts
import { analyzeClarity, renderClarityReport, type ScenarioResult } from "@narrativetrace/clarity";

const result = analyzeClarity(tree);
const scenarios: ScenarioResult[] = [{ scenario: "Guest books a room", result }];
console.log(renderClarityReport(scenarios));
```

生成一份包含评分表和问题表(如果有)的 Markdown 报告:

```markdown
## Clarity Report — Guest books a room
Overall: 0.95 (high)

| Component  | Score |
|------------|-------|
| Method     | 0.98  |
| Class      | 1.00  |
| Parameter  | 0.90  |
| Structural | 1.00  |
| Cohesion   | 0.85  |
```

### 套件报告

```ts
const scenarios: ScenarioResult[] = [
  { scenario: "Guest books a room", result: result1 },
  { scenario: "Legacy data processing", result: result2 },
];
console.log(renderClarityReport(scenarios));
```

生成所有场景的排名摘要。评分低于 0.7 的场景会获得包含各项具体问题的详细分解。

### JSON 导出

```ts
import { exportClarityJson, exportClarityJsonReport } from "@narrativetrace/clarity";

// 单个场景
const json = exportClarityJson(result, { scenario: "Guest books a room" });

// 多场景报告
const reportJson = exportClarityJsonReport(scenarios);
```

## Vitest 集成

将 `"clarity-json"` 格式与 `createNarrativeTest` 搭配使用:

```ts
import { createNarrativeTest } from "@narrativetrace/vitest";

const test = createNarrativeTest({
  outputDir: "narrativetrace-output",
  formats: ["md", "clarity-json"],
});

test("guest books a room", ({ narrativeContext }) => {
  // ... 测试代码
});
```

每次测试之后,都会在追踪输出旁写入一个 `.clarity-json` 文件。

## 静态扫描器 CLI

静态扫描器直接分析源文件——无需测试:

```bash
npx tsx tools/clarity-scan.ts
```

### 选项

| Flag | Effect |
|------|--------|
| `--min-score=0.80` | 若有任何类的评分低于该阈值,则以错误退出 |
| `--json` | 以 JSON 而非 Markdown 形式输出 |

### 示例

```bash
# 扫描所有包,输出人类可读的结果
npx tsx tools/clarity-scan.ts

# 在 CI 中强制执行最低评分
npx tsx tools/clarity-scan.ts --min-score=0.80

# 为工具链输出 JSON
npx tsx tools/clarity-scan.ts --json
```

### 工作原理

1. 在各个包中查找所有 `.ts` 源文件(排除测试和声明文件)
2. 使用 TypeScript Compiler API 解析每个文件
3. 提取类及其方法和参数
4. 对每个类运行 `analyzeClarity()`
5. 渲染清晰度报告,若低于阈值则以错误退出

## CI 强制执行

清晰度是一道构建门禁,而不仅仅是一份报告。有两个入口点会强制执行它,并且当命名质量的预算被突破时,二者都会以非零状态退出,从而使 CI 构建失败。

### `check` 门禁

根级的 `pnpm run check` 质量门禁会通过 `clarity:gate` 脚本,将清晰度门禁作为其中一个阶段来运行:

```bash
# pnpm run clarity:gate 实际运行的内容:
tsx tools/clarity-scan.ts --min-score 0.4 --max-high-issues 15
```

该门禁会静态扫描每一个 `packages/*/src` 源文件,为每个类评分,并在任意类的评分低于 `0.4` **或** 套件产生的 HIGH 严重级别问题超过 `15` 个时,使构建失败。调整这两个数字即可移动这道门槛。

### `tools/clarity-scan.ts` 的标志

静态扫描器同时接受 `--flag value` 和 `--flag=value` 两种形式:

| Flag | Effect |
|------|--------|
| `--min-score <n>` | 若任何被扫描的类评分低于 `<n>`,则失败 |
| `--max-high-issues <n>` | 若套件的 HIGH 严重级别问题超过 `<n>` 个,则失败 |
| `--warn-only` | 将违规打印为 `warning:`,但以 `0` 退出(只报告不阻断) |
| `--format <both\|md\|json>` | 与 `--output-dir` 搭配使用时,指定要写入哪些套件工件 |
| `--output-dir <dir>` | 将 `clarity-report.md` 和/或 `clarity-results.json` 写入 `<dir>`,而不是打印出来 |
| `--json` | 将套件的 JSON 打印到 stdout,而不是 Markdown |

**Exit codes:** `0` 表示通过,`1` 表示门禁失败(未加 `--warn-only` 时出现 `--min-score` 或 `--max-high-issues` 违规),`2` 表示用法错误(未知的 `--format` 取值)。以下是 CI 中的调用示例:

```bash
# 严格门禁——遇到第一个低于阈值的类即失败
tsx tools/clarity-scan.ts --min-score 0.80

# 对 HIGH 问题数量设置门禁,并输出工件供流水线归档
tsx tools/clarity-scan.ts --max-high-issues 15 --output-dir clarity-out --format both

# 仅观察:在 PR 上呈现警告,暂不使构建失败
tsx tools/clarity-scan.ts --min-score 0.80 --warn-only
```

### `narrativetrace-clarity` 可执行文件

`@narrativetrace/clarity` 还附带一个 `narrativetrace-clarity` 可执行文件。它不扫描源码,而是对一份**已经累积好**的套件 `clarity-results.json`(即 Vitest reporter 写入的文件——见下文)重新渲染并施加门禁,因此它适合放在测试套件运行之后的流水线阶段中:

```bash
narrativetrace-clarity --min-score 0.4 --max-high-issues 15
```

| Flag | Effect |
|------|--------|
| `--input <file>` | 要读取的结果文件(默认为 `<output-dir>/clarity-results.json`) |
| `--output-dir <dir>` | 重新渲染的工件写入位置(默认为 `.`) |
| `--format <both\|md\|json>` | 要重新渲染哪些工件 |
| `--min-score <n>` | 若某个场景评分低于 `<n>`,则失败 |
| `--max-high-issues <n>` | 若套件超过 `<n>` 个 HIGH 严重级别问题,则失败 |
| `--warn-only` | 将违规打印为 `warning:` 并以 `0` 退出 |

**Exit codes:** `0` 表示通过,`1` 表示门禁失败或 IO 错误(例如输入文件缺失或无法读取),`2` 表示用法错误(未知的 `--format` 取值或任何未知参数)。

### 从 Vitest 生成结果文件

门禁的输入由 Vitest 的 `ClaritySuiteReporter` 产生。当一次运行中的每个测试文件都执行完毕后,它会为整个套件恰好写入**一个** `clarity-results.json` 和**一个** `clarity-report.md`(写入 reporter 的 `outputDir`,默认是 `narrativetrace-output`)。没有清晰度元数据的运行不会写入任何内容。将 `narrativetrace-clarity --input` 指向该 `clarity-results.json`,即可基于套件整体的命名质量对构建施加门禁。

## NLP 组件

清晰度模块使用手工编写的 NLP,没有任何外部依赖:

| Component | Purpose |
|---|---|
| `IdentifierTokenizer` | 将 camelCase、snake_case、下划线以及数字边界拆分为 token |
| `VerbDictionary` | 将动词分类为领域/标准/泛化/布尔类别,覆盖 500 多个领域动词(包括由搭配/角色推导出的覆盖) |
| `RoleSuffixDictionary` | 对类后缀进行归类(设计模式、功能性、泛化) |
| `GenericTokenDetector` | 对 token 特异性进行分级(无意义 -> 领域专属) |
| `AbbreviationDictionary` | 按三个层级(通用、广为人知、有歧义)为 187 个缩写评分 |
| `MorphologyAnalyzer` | 通过后缀(-tion、-ize、-able)识别词性 |
| `CollocationDictionary` | 在 209 个合并名词范围内校验动词-名词搭配(领域映射的合并语义) |
| `CohesionScorer` | 检查方法动词与类角色预期的一致性 |
| `DomainVocabulary` | 项目自己的词汇,读自已提交的术语表;在不推翻上述任何词典的前提下对其进行扩展 |

## 词典护栏

清晰度词典受到自动化护栏的保护:

- 基于属性的不变量测试(`fast-check`)验证搭配、角色预期和缩写在查找时不区分大小写。
- 一致性检查验证搭配动词和角色预期动词始终能被 `VerbDictionary` 正确分类。
- 漂移防护测试对词典规模强制执行保守的下限,并在测试运行期间打印当前指标。
