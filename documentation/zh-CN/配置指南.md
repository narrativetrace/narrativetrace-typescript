# NarrativeTrace TypeScript 配置指南

[English](../configuration-guide.md) | [Español](../es/guia-de-configuracion.md) | [Português](../pt-BR/guia-de-configuracao.md) | **简体中文**

本指南介绍 NarrativeTrace TypeScript 的运行时配置与测试配置。

## 1. 追踪级别(`NarrativeTraceConfig`)

`SyncNarrativeContext` 和 `AsyncNarrativeContext` 使用 `NarrativeTraceConfig`，默认值为 `"detail"`。

```ts
import { NarrativeTraceConfig, SyncNarrativeContext } from "@narrativetrace/core";

const config = new NarrativeTraceConfig("narrative");
const context = new SyncNarrativeContext(config);
```

可用级别：

| 级别 | 行为 |
|---|---|
| `"off"` | 不捕获任何追踪 |
| `"errors"` | 仅捕获异常路径 |
| `"summary"` | 捕获根入口、最深的叶节点与完整的异常链 |
| `"narrative"` | 捕获完整调用流程，但不记录参数值 |
| `"detail"` | 捕获完整调用流程，包含参数值与返回值 |

支持在运行时切换级别：

```ts
config.level = "errors";
```

### 级别辅助函数

```ts
import { isActiveLevel, isEnabled } from "@narrativetrace/core";

isActiveLevel("off");       // false
isActiveLevel("errors");    // true
isEnabled("detail", "narrative"); // true — detail 不低于 narrative
isEnabled("errors", "detail");    // false — errors 低于 detail
```

## 2. Vitest 配置

### 基础夹具(无输出)

```ts
import { narrativeTest } from "@narrativetrace/vitest";

narrativeTest("my test", ({ narrativeContext }) => {
  // narrativeContext 是一个使用默认配置的 SyncNarrativeContext
});
```

### 带文件输出

```ts
import { createNarrativeTest } from "@narrativetrace/vitest";

const test = createNarrativeTest({
  outputDir: "narrativetrace-output",      // 默认: "narrativetrace-output"
  formats: ["md", "json", "mmd", "puml"],  // 默认: ["md", "json", "mmd"]
});
```

### 输出布局

产物按测试*模块*(测试文件的基础名 —— 相当于 Java 版本中测试类目录的平台等价物)分组，图表则存放在一棵镜像目录树中：

```
narrativetrace-output/
  order-service/                 # 来自 order-service.test.ts
    places_order.md              # 叙事 + YAML frontmatter
    places_order.json            # 规范 JSON
  diagrams/
    order-service/
      places_order.mmd           # Mermaid 时序图
```

不同 `describe` 块中同名的测试仍保持独立：套件链是文件名的一部分。模块名和测试名都会被净化(sanitize)，因此两者都不能写到 `outputDir` 之外。

### 可用格式

| 格式 | 扩展名 | 渲染器 |
|--------|-----------|----------|
| `"md"` | `.md` | `renderMarkdown()`，附带场景名称 |
| `"json"` | `.json` | `exportJson()`，附带场景元数据 |
| `"mmd"` | `.mmd` | `renderMermaidSequence()` |
| `"puml"` | `.puml` | `renderPlantUmlSequence()` |
| `"clarity-json"` | `.clarity-json` | `exportClarityJson()`，附带分析结果 |
| `"canonical-json"` | `.canonical.json` | `exportCanonicalJson()` —— 扁平的条目列表 |

`"json"` 和 `"canonical-json"` 为不同的读者描述同一条追踪。`"json"` 是嵌套的章节树信封格式，为人类以及遍历调用树的工具而设计。`"canonical-json"` 是 [`schema/entry.schema.json`](../../schema/entry.schema.json) 所声明的进入/退出记录扁平数组 —— 每个事件一条记录，采用 OTel 对齐的键名，是跨平台一致性 fixture 的编写格式。两者可以只选一个，也可以两者都要。

它是刻意设计成确定性的：在没有 span 上下文的情况下捕获的追踪(例如一个普通的单元测试)会得到顺序生成的合成 span id 与一个固定的合成 trace id，因此同一个测试运行两次会产生完全相同的字节。`NARRATIVETRACE_FORMATS` 中还接受别名 `canonical` 和 `canonicalJson`。

### 场景名称

测试名称会被用作输出文件中的场景名称。文件名会被净化(移除非字母数字字符，空格替换为下划线)：

- `"customer places order"` → `customer_places_order.md`
- `"order with quantity < 1 fails"` → `order_with_quantity__1_fails.md`

### 场景标题转换

`frameScenario()` 会将测试名称转换为人类可读的场景标题：

- `customerPlacesOrder` → "Customer places order"
- `customer_places_order` → "Customer places order"
- `test_should_validate_input` → "Should validate input"

## 2b. 配置来源

配置按优先级从高到低的顺序解析。每个来源只会补全在它之上的来源未设置的部分：

| 优先级 | 来源 | 示例 |
|---|---|---|
| 1(胜出) | 显式代码选项 | `createNarrativeTest({ level: "summary" })` |
| 2 | 环境变量 | `NARRATIVETRACE_LEVEL=off pnpm test` |
| 3 | 项目配置文件 | 仓库根目录下的 `narrativetrace.config.json` |
| 4 | 内置默认值 | `level: "detail"`、`outputDir: "narrativetrace-output"`、`formats: ["md", "json", "mmd"]` |

### 项目配置文件

在项目根目录放置**其中一个**文件 —— 具体用哪个由你的团队决定：

```jsonc
// narrativetrace.config.json (或: .narrativetracerc.json)
{
  "level": "summary",
  "outputDir": "narrativetrace-output",
  "format": "md,json"
}
```

键名与环境变量一致，只是去掉了 `NARRATIVETRACE_` 前缀：`level`、`output`、`outputDir`、`format`。未知的键与类型错误的值都会被忽略，因此一个误写的配置项永远不会导致运行失败。

### 出现两个配置文件是一个错误，而不是抛硬币决定

同时提供**两个**受支持的文件名，会立即导致运行失败：

```
DuplicateConfigurationError: Multiple NarrativeTrace configuration sources
found: narrativetrace.config.json, .narrativetracerc.json.
Keep exactly one and delete the rest.
```

同样的规则也适用于内容不是合法 JSON、或顶层不是一个对象的配置文件。悄悄地偏向某一个来源，正是一次让旧配置死灰复燃的合并操作能够数月不被察觉的原因 —— 因此这里选择直接停止运行。而写错的*值*则会被更温和地对待：一个无法识别的 `level` 会降级为默认值，而不会导致失败。

你也可以自行调用 `@narrativetrace/core-node` 中的 `resolveConfig()` 来解析配置；每个来源都可以注入(`{ env, projectRoot, read, fallbackLevel }`)，便于测试。

## 3. 渲染选项(`renderValue`)

`renderValue()` 函数将值序列化为字符串，它接受一些选项来控制截断行为：

```ts
import { renderValue } from "@narrativetrace/core";

renderValue(someObject, {
  maxStringLength: 200,   // 默认: 200 — 超过该长度的字符串将被截断
  maxArrayItems: 5,       // 默认: 5 — 显示数组的前 N 个元素
  maxObjectKeys: 5,       // 默认: 5 — 显示对象的前 N 个键
});
```

| 选项 | 默认值 | 效果 |
|--------|---------|--------|
| `maxStringLength` | 200 | 超过该长度的字符串会被截断，并附加 `"..."` |
| `maxArrayItems` | 5 | 数组显示前 N 个元素，随后附加 `... (N total)` |
| `maxObjectKeys` | 5 | 对象显示前 N 个键，随后附加 `... (N total)` |

### 类型处理

| 类型 | 渲染为 |
|------|-------------|
| `null` | `"null"` |
| `undefined` | `"undefined"` |
| `string` | `"\"hello\""`(加引号) |
| `number` | `"42"` |
| `boolean` | `"true"` |
| `bigint` | `"42n"` |
| `symbol` | `"Symbol(name)"` |
| `function` | `"<function>"` |
| `Array` | `[1, 2, 3]` |
| `Object` | `{"key": "value"}` |
| 循环引用 | `"<circular>"` |

## 4. Markdown 选项

`renderMarkdown()` 接受用于控制渲染输出的选项：

```ts
import { renderMarkdown } from "@narrativetrace/core";

const markdown = renderMarkdown(tree, {
  scenarioName: "Customer places order",   // 会出现在 YAML frontmatter 中
  slowThresholdMs: 200,                     // 默认: 200 — 标记慢调用
});
```

| 选项 | 默认值 | 效果 |
|--------|---------|--------|
| `scenarioName` | (无) | 添加到 YAML frontmatter 中 |
| `slowThresholdMs` | 200 | 耗时超过该阈值的调用会带上警告标记 |

### 输出格式

Markdown 输出包含 YAML frontmatter 与一个嵌套的项目符号列表：

```markdown
---
scenario: Customer places order
methods: 5
result: success
---

- `OrderService.placeOrder(customerId: "C1", productId: "P1", quantity: 2)` → `{"orderId": "ORD-1", ...}`
  - `CustomerService.findCustomer(customerId: "C1")` → `{"id": "C1", ...}`
  - `PaymentService.charge(customerId: "C1", amount: 59.98)` → `{"transactionId": "TX-1", ...}`
```

## 5. 参数脱敏(`@notTraced`)

将敏感参数标记为脱敏，使其值永远不会出现在追踪输出中：

```ts
import { notTraced } from "@narrativetrace/proxy";

class AuthService {
  @notTraced(1) // 对索引为 1 的参数进行脱敏
  login(username: string, password: string) {
    // ...
  }
}
```

追踪输出会显示 `***`，而不是实际的值：

```
AuthService.login(username: "admin", password: ***)
```

如需手动(非装饰器)脱敏，请参阅[装饰器指南](装饰器指南.md)。

## 6. Proxy 选项

`traceObject()` 接受可选配置：

```ts
import { traceObject } from "@narrativetrace/proxy";

const traced = traceObject(service, context, paramNames, {
  className: "OrderService",      // 覆盖类名(默认: constructor.name)
  includeReturnValues: true,      // 捕获返回值(默认: true)
});
```

| 选项 | 默认值 | 效果 |
|--------|---------|--------|
| `className` | `target.constructor.name` | 追踪中显示的类名 |
| `includeReturnValues` | `true` | 为 `false` 时，不渲染返回值 |

## 7. 按环境推荐的默认值

| 环境 | 建议级别 | 建议输出 |
|---|---|---|
| 本地功能开发 | `"detail"` | `formats: ["md", "json"]` |
| CI 测试运行 | `"narrative"` 或 `"summary"` | `formats: ["md"]` |
| 生产环境 | `"errors"`(或 `"off"`) | 不输出文件 |

## 8. 事件管道缓冲(`BufferedEventConsumer`)

使用默认参数构造的上下文会得到一个 `DualPathPipeline(null, new BufferedEventConsumer())`。缓冲路径是尽力而为的路径：一次被追踪的调用只需付出一次环形缓冲区写入的代价，随后一个定时器会在后续的 tick 中把环中的数据排空到事件存储(以及任何订阅者)中。

```ts
import { BufferedEventConsumer, DualPathPipeline, SyncNarrativeContext } from "@narrativetrace/core";

// 默认值 — 针对小型虚拟机、容器或云函数上的长生命周期进程而设定的大小。
const context = new SyncNarrativeContext(config);

// 每个默认值都可以按位置覆盖: (capacity, drainIntervalMs, chunkSize)
const highThroughput = new BufferedEventConsumer(262_144, 50, 4096);
const pipeline = new DualPathPipeline(null, highThroughput);
const context2 = new SyncNarrativeContext(config, undefined, pipeline);
```

| 选项 | 默认值 | 效果 |
|---|---|---|
| `capacity` | `65536`(2^16) | **环的固定大小**，因此也是未排空事件数量的上限 |
| `drainIntervalMs` | `100` | 排空周期。定时器只在有事件等待时运行 |
| `chunkSize` | `1024` | 每个 tick 排空的事件数 |

### 缓冲区大小固定 —— 它从不增长

`capacity` 是环的大小，而不是它逐步逼近的上限。没有初始容量，也没有增长因子：大小的确定是一次性的决策，在一开始就完成。

- **在第一个事件到来之前不会分配任何内存。** 一个空闲的上下文 —— 一个从不进行追踪的测试、一个提前返回的请求 —— 会保持 `allocatedCapacity === 0`。第一个被缓冲的事件会**一次性整体**分配大小为 `capacity` 的环，并且在消费者的整个生命周期内(包括每次 `clear()` 之后)始终保持这个大小。
- **达到上限时，缓冲区会丢弃事件，而不会阻塞。** 最旧的未读事件会被覆盖，并计入 `consumer.overflowCount()`。(`droppedCount()` 是另一个不同的数字：表示因为*订阅者*仍处于忙碌状态而未能投递的事件。)`overflowCount()` 不为零只说明一件事：`capacity` 设置得太小了。

### 短生命周期的上下文：把容量调小

由于环是整体分配的，一个上下文中的*第一次被追踪的调用*要为整个 `capacity` 付出代价。对于构建一个上下文并长期持有它的服务器来说，这个代价可以忽略不计；但对于每请求、每测试、每次浏览器点击都新建一个上下文的模式来说，这个代价并不是免费的。按每个全新消费者测得的开销(分配、两个事件、排空、关闭)：

| `capacity` | 每个上下文的开销 |
|---|---|
| 1,024 | 0.8 µs |
| 2,048 | 1.1 µs |
| **8,192** | **3.8 µs** |
| 16,384 | 31.7 µs |
| 65,536 | 99.0 µs |

8,192 与 16,384 之间的跳变并不是一条平滑曲线：16,384 个指针正好是 128 KB，这正是 V8 把底层存储移入大对象空间(large-object space)的临界点。让短生命周期上下文的环保持在这条线以下。

`@narrativetrace/vitest` 已经替你做了这件事 —— `createNarrativeTest()` 会为每个测试提供一个 `DEFAULT_TEST_BUFFER_CAPACITY`(8,192)的上下文，可以按夹具通过 `createNarrativeTest({ bufferCapacity: 32_768 })` 覆盖。如果某个捕获窗口发生了溢出，运行结果会明确说出来：一行警告注明数量以及应当调高到的值，并在 Markdown 与图表产物的页脚中附上同样的一句话。请注意，该集成是**显式**传入大小的 —— 运行时永远不会检测测试框架并据此改变行为，因为一个在测试下表现不同的运行时，其测试也就什么都证明不了。

对于你自己的短生命周期上下文，请在构建它们的接缝处做同样的事：

```ts
// 每个 HTTP 请求一个上下文,大小按请求而非进程来设定。
const buffer = new BufferedEventConsumer(4096);
const ctx = new SyncNarrativeContext(config, undefined, new DualPathPipeline(null, buffer));
try {
  /* ...处理请求、捕获追踪... */
} finally {
  ctx.eventPipeline.close();
}
```

### 排空定时器，以及 `close()`

- **排空定时器在第一个被缓冲的事件到来时启动，只有当缓冲区排空为空时才会停止**，并在下一个事件到来时重新启动。它绝不会在缓冲区非空的情况下被清除，因此一次突发流量之后即便归于沉寂，也仍会被排空到底 —— 不会有任何事件被搁置。一个空闲的消费者不持有任何定时器，因此在不调用 `close()` 的情况下丢弃它也不会留下任何被引用的对象。在 Node 上，该定时器还被 `unref` 处理过，因此一个待处理的排空操作永远不会让进程保持存活。

**只要存在一个生命周期，就仍应调用 `close()`** —— 请求结束、测试收尾、关闭进程。这是确定性的路径：它会排空尾部事件，使关闭时不会丢失它们；它会立即停止定时器，而不是等到下一个 tick；并且会释放 `whenClosed()`/`whenCountReached()` 的等待者。`DualPathPipeline.close()` 与 `context.eventPipeline.close()` 都会转发到它。

### 容量估算规则 —— 何时需要调大

对于一个长生命周期的进程，环只需要覆盖*在一次排空停滞期间*产生的事件 —— 它每 100 ms 排空一次，因此要让默认值溢出，需要在一个窗口内持续产生约 655,000 事件/秒。持久性并不是这条路径的职责，管道的同步消费者才负责这件事。

```
capacity ≈ 峰值事件数/秒 × 可容忍的最长排空停顿(秒)
分配后占用的内存 ≈ capacity × ~300 B/事件      (65,536 ≈ ~20 MB)
```

举例说明 —— 一个服务，1,000 请求/秒，每个请求 50 次被追踪的调用，每次调用 2 个事件(进入 + 退出)：

```
1,000 × 50 × 2            = 100,000 事件/秒
100,000 × 0.5 秒停顿      =  50,000 事件  →  低于 65,536, 默认值足够
```

把速率或可容忍的停顿翻一倍，你就会超出默认值：此时传入更大的 `capacity`(并在预发布环境中检查 `overflowCount()`)。内存随之线性增长 —— 262,144 大约是 80 MB，这也是它不再作为默认值的原因。缓冲区永远不会自己腾出空间，因此你传入的数字就是你得到的数字：太小会丢弃事件，太大则会让每一个分配它的上下文都要付出代价。
